Each page below composes the same templates and the same handler shape. What changes is only what the slow dependency does, and whether its await block declares a recover clause.

Success

/profile

Two dependencies settle after the page has already been delivered. Each section replaces its own fallback as its data arrives.

Failure, contained

/profile?fail=recommendation

The recommendation fails, and its boundary declares recover. The clause renders in place of that section and the rest of the page is untouched. The response stays 200, which is honest: most of it worked.

Failure, unhandled

/profile?fail=orders

The orders fail, and their boundary declares no recover. The template said what to show while waiting and what to show on success, and nothing about failure, so the framework replaces the page with an error document rather than leaving a section claiming to load forever.

The status is still 200, because it went out with the shell long before the failure was known. Only the log can carry that truth.

Failure, before anything was sent

Set html.streaming = false in config.dev.toml, then reload the unhandled case.

The same templates render as one buffered response, so the failure happens while nothing is committed. That response answers with a real 500 instead of patching a page that already left. Only one of the two branches can still tell the truth in its status line, and it should.

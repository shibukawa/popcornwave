# Report: wiring the typed server action, and two things it meets

Measured against **tinybind-go v0.5.10** on 2026-08-14, by wiring every caller
side of `requirement:typed-server-action` and declaring one in a real page tree.

The feature works. Discovery, the annotation seam, the published name, the
signature reading, the wrapper's shape and the registration are all as specified,
and the parts that are ours are built and green. Two defects stop a declared
action from compiling in a route package, and neither is reachable from the
tests that cover the feature, because both need a package with more than one
generated artifact.

---

## What is wired on this side

- `pw.ServerAction(fn, name...)`, forwarding to `httpbind.ServerAction`.
- `HandlerShape.Declaration` set for both transports, stating the identifier —
  which was needed exactly as the release notes say: our path ends in
  `popcornwave` and our package is `pw`, so a derived name would have missed.
- Typed actions carried from `routetree.Result.Actions` to the binding phase per
  route package, through `Options.WithServerActionsFor`.
- The published name read from `Action.Published` rather than the Go name, so a
  script calls `actions.rename` where the address still carries `Rename`.

Verified end to end: a declared `func profile(ctx context.Context, id string)
(Profile, error)` produced the table entry, the hash, `Typed: true`, the
registration naming `id_.ActionProfile`, and a wrapper whose body is exactly the
shape the requirement describes.

---

## 1. The wrapper and its decoder land in different artifacts

`planServerActions` analyses the argument struct with an **empty source path**:

```go
tp, ok, err := analyzeStruct(action.inputTypeName(), "", st, …)
```

`goBindingArtifacts` then groups `plan.Types` by `t.SourcePath` and emits one
artifact per source. So the input struct groups under `""`, into an artifact
whose `OutputBase` is `artifactBase("")`.

Meanwhile `emitServerActions` is called at the end of `emitSelectedFor`
unconditionally — it iterates `plan.ServerActions` and consults no `selected`
map. So the wrapper and the input struct's *declaration* are written into every
per-source artifact, while the input struct's *decoder* is written into the
degenerate one.

What we measured, in a route package whose `action.go` declares the models:

```go
// action_pw_gen.go — emitted for action.go
type actionProfileInput struct{ Id string `json:"id"` }

func ActionProfile(w http.ResponseWriter, r *http.Request) {
	…
	input, err := decodeactionProfileInputBytes(body)   // undefined
```

`appendProfileJSON` **is** emitted, so the encode half of the declared usage
reaches the right artifact; only the decode half does not.

`generator/serveraction_test.go` does not meet this because it emits with
`selected == nil`, which is the one-artifact path.

**A second consequence of the same unguarded call:** a package with two Go
sources carrying bindings gets the wrapper and the input struct declared twice,
in two files of one package. We did not reproduce that — our fixture has one
such source — but it follows from the same line.

**What would fix it:** give the input struct the source path of the file
declaring the action, so it groups with the wrapper, and select the actions
`emitServerActions` writes by the same grouping.

## 2. A generated wrapper is rediscovered as a raw action

The wrapper is an exported function taking exactly the transport types and
returning nothing, in a route package. That is the raw admission rule, so the
next generation run discovers it as an action of its own:

```go
{Pattern: "POST /_action/348993915ad1/ActionProfile", …,
 Handler: "ActionProfile", Published: "actionProfile", Typed: false},
```

It gets its own hash, its own address, its own published name, and its own
registration, beside the typed action it exists to serve.

The reason is a header mismatch. The page tree's own output carries

```
// Code generated by Popcorn Wave via TinyBind; DO NOT EDIT.
```

and the binding phase's output — the wrapper's file — carries

```
// Code generated by tinybind; DO NOT EDIT.
```

`rule:generated-source-not-discovered` is what should exclude it. On our side
`generator.Options.GeneratedHeaders` names our own prefix, which is right for
the files we generate; the wrapper is not one of them.

We can work around it by naming tinybind's prefix too, and we would rather not:
a framework listing another module's header string to avoid rediscovering that
module's output is a coupling that goes stale silently, and it would also
exclude every hand-written file somebody happened to head that way.

**What would fix it, in preference order:** action discovery skipping a file it
recognizes as generated regardless of who generated it; or `ActionWrapperName`
producing a name discovery excludes by construction; or the wrapper being
emitted unexported with the registration naming it through a generated
reference.

---

## What we did with the fixture

Backed the declaration out, so the tree compiles. Everything else stands: the
annotation, the declaration wiring, the per-package hand-off and the published
name are committed and covered. The fixture carries a comment saying where the
declaration goes when these two are answered — re-adding it is one paragraph.

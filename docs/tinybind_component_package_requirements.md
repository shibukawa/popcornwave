# Component Package Distribution — Requirements For TinyBind

Report from Popcorn Web to `github.com/shibukawa/tinybind-go`, 2026-08-02.

## What we are building

Popcorn Web targets one application today. Every source belongs to one project, is
generated by that project's `pw generate`, and the generated Go is excluded from version
control and recreated before each build.

We want a capability to be publishable as an ordinary Go module and installable by naming
that module in the project's own config file — the blank import that links it is generated
from the declaration. Inside that module the generated Go is **committed**, because
the consumer never runs a generator over a dependency: the module cache is read only, and
our generation scope is a list of project-relative directories by construction. This is
the same model your `requirement:modular-package-generation` already states from the other
side — one invocation analyzes one package, and an imported generated package is reused
rather than regenerated.

The design is recorded in our catalog under `requirement:component-package-distribution`,
with `concept:component-package`, `decision:committed-package-artifacts`, and
`decision:package-contract-split` beside it.

## What needs nothing from you

Most of it. A package that ships handlers, a page tree, an extension registration, its own
templates, and its committed generated code is expressible with TinyBind as it stands. We
scaffold it, generate it in its own repository, gate it with `pw generate --check`, and the
consumer compiles it with the Go compiler alone. That shape is stage one and we are
building it now.

We are raising four items because the second shape — a module that exports **components**
for a consumer's own templates to call — is blocked, and because committing generated code
makes one existing unstated guarantee load-bearing.

## Ask 1 — an external component declaration must be able to name another module

**Priority: should. Blocks the component-library shape entirely.**

`requirement:cross-template-components` resolves a component exported from another
*template file*. `requirement:template-file-scope` leaves open "whether external
declarations name a path, a module, or a configured generation unit", and
`decision:library-component-seams` records that a cross-package component still has no way
in and that the asset seam has to serve it.

Two things are missing, and the second is the harder one:

1. **Notation.** There is no spelling for a target outside the generation unit.
2. **Resolution input.** Cross-file resolution reads the other template file. A consumer
   has the dependency's *generated Go* and not its `.pw.html`. Reading the dependency's
   templates out of the module cache would be exactly the dependency rescan that
   `requirement:modular-package-generation` forbids.

Proposed shape:

- The declaration names a **Go import path plus the exported component name**. The import
  path is the identity the consumer already resolved through `go.mod`, so no new
  addressing scheme is introduced.
- Resolution reads the **generated package**, not the templates.
- The generated package carries an **exported, machine-readable signature** per exported
  component, emitted beside the renderer. `htmlbind.Signatures` already exposes this
  in-process; what is missing is a persisted form a separate generator run can verify
  against.
- Verification is unchanged from the cross-file case: parameter names, types, slots, and
  output type must match, and a mismatch names both positions.

The signature artifact doubles as the compatibility surface: a package that changes a
component signature then breaks its consumers at generation time with a diagnostic, rather
than at link time with a Go type error.

Acceptance we would test against:

- a component exported by an imported module is callable from a consumer template with
  full parameter type checking;
- the consumer's generation reads no `.pw.html` outside its own project;
- a slot on a cross-module component is filled exactly as a same-file one is;
- a project using no cross-module component regenerates byte-identical output.

Our id: `requirement:cross-package-components`.

## Ask 2 — the library case of component assets, with the URL function

**Priority: should. Depends on ask 1.**

This is your `requirement:component-asset-requirements` with its own open question —
"whether a cross-package template component reaches this seam at all" — answered **yes**.

The authoring half shipped on 2026-07-31: a component's inline script is extracted into a
content-hashed file under `PublicDir` and referenced from the merged head. That serves a
component declared in a template file of the unit being compiled, and it writes a
filesystem artifact. Neither property survives distribution: the package owns no public
directory in the consumer, and a written file is not something a module ships into a
consumer's tree.

What we need from the designed-but-unbuilt half:

- **The embedded table, not the written files.** We serve package assets from embedded
  bytes under a reserved content-addressed path (`/_pw/pkg/<digest>/<name>`), because a
  TinyGo target may have no filesystem and nothing may be written into the consumer's
  project tree. Our `requirement:package-asset-delivery` owns the serving.
- **The caller-supplied URL function.** Only the framework knows the reserved prefix and
  the digest path. The package must not choose a URL.
- **The static required set on the plan value.** Our fragment responses and live
  deliveries can both insert a component whose script was not in the first render, so the
  document has to be able to carry every script a later delivery might need.
- **The fragment-path report.** A response with no document shell must report an asset it
  cannot deliver, exactly as a fragment response already refuses head contributions rather
  than dropping them.

Our interim, which works and does not scale: the package documents its asset name and the
application writes one tag in its document shell. It breaks silently when a package upgrade
adds an asset, which is the reason to close this rather than the reason to hurry.

Our id: `requirement:package-component-assets`.

## Ask 3 — state what runtime a generated artifact links against

**Priority: should. Independent of asks 1 and 2, and the cheapest of the four.**

This one is new and it is not about components.

Today an application regenerates before every build, so the generator and the runtime are
one dependency at one version and skew is impossible. Committing generated code into a
published module breaks that: the artifact is frozen at publish time, `go.mod` resolution
picks the runtime at build time, and Go selects the higher of the two. **The pair that runs
was never the pair that was tested**, for every consumer whose application resolved a newer
version than the package author did.

Your catalog records per-release compatibility notes for features, and states nothing about
generated output against a different runtime version. The variance is real and observable:
between two v0.2 releases the dynamo runtime entries lost their client parameter, which is
a breaking change to generated call sites rather than to a public API a human wrote.

What we are asking for is a statement, not a mechanism:

- each release names the generator versions whose output it accepts;
- the scope is the runtime entries generated code calls, which is far narrower than the
  public API;
- a release that breaks generated output says so, so a downstream can refuse the pair
  before the compile error.

A stronger form — a generator-version constant in generated output that the runtime can
refuse with a named error — is only worth building if the note cannot be relied on. A
compile error is an acceptable failure mode as long as the note exists.

Meanwhile we record the generating versions in the package manifest, state our own support
window in `policy:package-compatibility` derived from testing rather than from a guarantee,
and report a package outside it from `pw doctor`. The residual we cannot remove is that a
minor release of yours can invalidate that window without warning.

Our id: `requirement:generated-code-version-tolerance`.

## Ask 4 — one package, several SQL dialects

**Priority: could. We have designed around it and are not blocked.**

A `.pw.sql` source compiles to one engine's placeholder syntax, selected as a required
generation input since v0.2.2. A distributable package cannot know its consumer's engine,
so a package that ships generated queries would be engine-locked at publish time.

We have made this a stated non-goal for the first shape: a component package ships no
`.pw.sql`, and a package needing SQL writes it by hand. That is a real cost — it gives up
the typed query path exactly where reuse would pay for it — but it is a cost we can carry.

If it is ever cheap on your side, the shape that would unlock it is one generation run
emitting one artifact set per declared dialect into distinguishable symbols or
subpackages, with the consumer's engine selecting between them at link time. We are not
asking for it now; we are recording why the non-goal exists so it is not read as a design
preference.

## Evidence and its limits

- Popcorn Web pins **tinybind-go v0.2.10**. We have not adopted v0.3.1.
- The claims above about what exists upstream are read from the **v0.3.1 `.knowledge`
  catalog** in the module cache, not verified against v0.3.1 source. Where your catalog
  marks something proposed or unbuilt we have taken that at face value.
- The claims about our own side — generation scope, the read-only module cache, our
  version-control policy, the asset path — are verified in this repository.
- Nothing here reports a defect. All four items are seams that were correctly closed for
  the single-application model and that distribution opens.

## Sequencing we would suggest

1. **Ask 3**, because it is a document rather than a change, and it is load-bearing for
   everything we publish from the day we publish it.
2. **Ask 1**, because it is what the component-library shape waits on and because its
   signature artifact is reusable by ask 2.
3. **Ask 2**, which reads much better once ask 1 exists and which has your own design
   already written.
4. **Ask 4**, if ever.

This matches your own sequencing rule from `decision:library-component-seams` — order by
readiness — rather than by what each item unblocks for us.

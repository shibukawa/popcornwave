import { Card, CardGrid } from '@astrojs/starlight/components';

Start with the unit Go already gives you: one `http.Handler`. It binds a
request, runs application logic, and writes a complete response through ordinary
navigation and form semantics. The result remains a small, practical TinyGo
target — without a component graph, patch protocol, hydration step, or browser
runtime.

<CardGrid>
  <Card title="Standard library first" icon="seti:go">
    Routing uses `net/http`'s own `ServeMux`: the same patterns, wildcards, and
    precedence. Handlers remain plain `http.HandlerFunc`.
  </Card>
  <Card title="Generated, not reflected" icon="setting">
    `pw generate` compiles templates, SQL, request binding, and OpenAPI into Go
    ahead of time. With no runtime reflection, the same code runs on
    **TinyGo**.
  </Card>
  <Card title="One command to a running app" icon="rocket">
    `pw init` scaffolds a complete project — handler, typed page, document
    shell, SQL, migration, error pages, Devbox — and `pw dev` watches it.
  </Card>
  <Card title="Operations included" icon="approve-check">
    Startup validation, `/healthz`, `/readyz`, `/openapi.json`, graceful
    shutdown, request IDs, access logs, and validated security headers.
  </Card>
</CardGrid>

Need richer interactions later? An opt-in server-driven UI layer extends the
same `net/http` foundation rather than replacing it. If an application does not
import that layer, it does not pay for it.

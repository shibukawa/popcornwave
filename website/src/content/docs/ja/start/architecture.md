Popcorn Wave の出発点は、サーバーレンダリングのアプリケーションも `net/http` の
アプリケーションらしく読めるべきだ、という馴染みのある制約です。オプションの
サーバー駆動 UI レイヤーは同じ土台を拡張しますが、ここで説明する内容はそのレイヤーに
依存しません。追加のランタイムをインポートしなければ、そのコストも発生しません。

## リクエストモデル

HTTP ハンドラが 1 つのリクエストをバインドし、アプリケーションロジックを実行して、
完全なレスポンスを 1 つ書き出します。ナビゲーションとフォームは、ブラウザ標準の
セマンティクスを保ちます。

| 関心事 | 動作 |
| --- | --- |
| 処理の単位 | 1 つの `http.Handler` |
| リンク | 完全なドキュメントリクエスト |
| フォーム | 通常の送信とリダイレクト |
| 変更操作 | ハンドラまたはアプリケーションサービス |
| 変更後のブラウザ既定 | Post/Redirect/Get |
| トランザクション境界 | `pw.Transaction` による明示的な指定 |
| クライアント側の拡張 | 任意 |

このモデルが意外性に乏しいのは意図的です。Go 開発者がすでに読めるハンドラは、
フレームワークを追加しても同じように読めるままです。

## 何が動き、どこから来たのか

1 つのリクエストで動く部品は、次の 4 つのいずれかです。自分が書いたコード、自分が
書いた何かから `pw generate` が書き出したコード、フレームワーク自身のコード、そして
標準ライブラリ。下の図は、リクエスト 1 往復をその区別で塗り分けたものです。

![http.Server、フレームワークのミドルウェア、http.ServeMux を経てハンドラに届き、生成されたバインダ・クエリ関数・コンポーネント関数を呼んだあとランタイムがレスポンスを書くまでの図](../../../../assets/diagrams/request-parts.svg)

下から読みます。`http.Server` が接続を受け、フレームワークのミドルウェアはルートごと
ではなく mux 全体を包み、`http.ServeMux` がハンドラを選びます。この経路に Popcorn Wave
の型は 1 つも出てきません。`pw.Run` がサーバーに渡すのは素の `http.Handler` で、あとは
道を空けるだけです。

生成されたコードが呼ばれ始めるのは、その上のハンドラからです。ハンドラが呼ぶ 4 つの
うち 3 つは `pw generate` が書いたもので、それぞれの真上に、生成元になった自分の
ソースがあります。

**リクエストバインダ**は、宣言した構造体から生成されます。どこから読むのか、何が
成り立っていなければならないのかをフィールドタグが宣言し、そこから作られたバインダは
その構造体の型で登録されます。`pw.Parse[Input]` はそれを引き当てるだけです。フィールドの
詰め替えを行うのは、構造体を覗くリフレクションではなく生成されたコードです。

**クエリ関数**は `.pw.sql` から生成されます。ファイルの中の名前付きステートメント
1 つが Go の関数 1 つになり、引数はステートメントのパラメータ、行はその隣で宣言した
レコード型に読み込まれます。マイグレーションで列名が変わったとき、止まるのは
リクエストではなくビルドです。

**コンポーネント関数**は `.pw.html` から生成されます。受け取るのは生成された
パラメータ構造体で、返すのは文字列ではなくフラグメントです。パラメータを 1 つ渡し
忘れればコンパイルエラーになり、エスケープはテンプレートを読んだ時点で位置ごとに
決まっています。生の出力を通す抜け穴は、意図的に狭くしてあります。

4 つ目は生成物ではありません。`pw.WriteHTML` はフレームワーク自身のランタイムで、
フラグメントをバッファに描画して検証し、そこで初めてステータス・ヘッダ・ボディを
コミットします。ステータスとヘッダが決まるのは、常にボディの最初の 1 バイトより
前です。

生成の見返りは 2 つあります。ひとつは、間違いがビルド時に前倒しされること。URL 属性に
`string` を入れたテンプレート、SELECT の列が結果型と合わないクエリ、新しい
テンプレートパラメータを渡し忘れたハンドラは、いずれもコンパイラが止めます。
もうひとつは、リクエストの経路からリフレクションが消えること。**TinyGo** が実用的な
ターゲットになるのは、こちらの効果です。

その生成されたコード自体も、Popcorn Wave が書いているわけではありません。このフレーム
ワークのために作られた [`tinybind-go`](https://github.com/shibukawa/tinybind-go) 由来で、
図にある 3 つの生成物は、その 4 レイヤーのうちの 3 つです。

| 図の中の部品 | 背後のレイヤー | そのレイヤーが他に担うもの |
| --- | --- | --- |
| リクエストバインダ | `httpbind` | バリデーション、JSON とストリーミングのレスポンス、OpenAPI |
| クエリ関数 | `sqlbind` | ステートメントの組み立て、結果のスキャン |
| コンポーネント関数 | `htmlbind` | レンダーチェーン、コンテキストに応じたエスケープ |
| — | `configbind` | 設定バインディング、スキャフォールド、サブコマンド |

`configbind` に対応する箱がないのは、その仕事が最初のリクエストより前に終わっている
からです。設定は起動時に 1 度だけバインドされます。Popcorn Wave はこの 4 つを `pw` の
背後にまとめるので、アプリケーションコードがインポートするのは 4 つではなく 1 つの
安定した API です。`pw.HTMLFragment` は `htmlbind.Fragment` そのもの（型エイリアス）で、
この 4 つの名前が現れるのは生成ファイルの中だけです。

## `pw generate` が書き出すもの

図に出ているのは、ハンドラが直接呼ぶ 3 つの部品です。全体でも、背後の仕掛けほど
長くはありません。

| ソース | 生成されるもの |
| --- | --- |
| `*.pw.html` | 型付きコンポーネント関数とパラメータ構造体 |
| `*.pw.sql` | context を取る型付きクエリ関数 |
| `pw.Parse[T]` の呼び出し箇所 | `T` のリクエストバインディング |
| `pw.WriteAPI[T]` / `pw.NewStream[T]` の呼び出し箇所 | `T` のレスポンスエンコーディング |
| `pw.RegisterConfig[T]` の呼び出し箇所 | `T` の設定バインディング |
| 上記すべて | OpenAPI 3.1 フラグメント |

いずれも生成元のソースの隣に、`_pw_gen.go` で終わる名前で置かれます。これらはビルド
出力です。`pw generate` が上書きし、`pw dev` はソースが変わるたびに再実行し、手で
編集する人はいません。

## 標準ライブラリとの互換性

`pw.NewServeMux` は通常の Go ビルドでは `*http.ServeMux` を返します。ラッパーではなく
型エイリアスです。パターン、ワイルドカード、優先順位は完全に標準ライブラリのものです。
同じセマンティクスを持つ別実装は TinyGo 向けにのみコンパイルされます。TinyGo にも
`ServeMux` 自体はありますが、Go 1.22 で入ったパスパラメータとメソッド指定が
0.41 時点では使えないためです。

これは全体を通じて同様です。ハンドラは `http.HandlerFunc`、ミドルウェアは
`func(http.Handler) http.Handler` であり、サーバー自体を自分で管理したい場合は
`pw.Middlewares` が素の `http.Handler` を返します。

## キャッシュ

3 つのレイヤーが独立して利用できます。

- HTTP のバリデータとレスポンスキャッシュ
- 生成された読み取りクエリの安全なキャッシュ
- アプリケーションキャッシュ

## 最小構成が除外するもの

このガイドで説明する範囲だけを使ったビルドは、小さく実用的な TinyGo ターゲットに
とどまることを目指しています。

- Popcorn Wave のブラウザランタイムなしで動作する
- 標準的なリクエストと完全なレスポンスを使う
- `net/http` のハンドラおよびミドルウェアと相互運用できる
- 型付きバインディング、設定、エラー、テンプレート、OpenAPI をサポートする
- ブラウザランタイムなしで Tailwind CSS を任意に利用できる
- コンポーネントグラフ、パッチプロトコル、ハイドレーションへの依存を含まない

最後の除外項目が境界を定めています。サーバー駆動 UI レイヤーはこの土台を拡張できますが、
土台の前提条件になることはありません。

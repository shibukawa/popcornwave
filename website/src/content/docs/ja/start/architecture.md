Popcorn Wave の出発点は、サーバーレンダリングのアプリケーションも `net/http` の
アプリケーションらしく読めるべきだ、という馴染みのある制約です。オプションの
サーバー駆動 UI レイヤーは同じ土台を拡張しますが、ここで説明する内容はそのレイヤーに
依存しません。追加のランタイムをインポートしなければ、そのコストも発生しません。

## リクエストモデル

HTTP ハンドラが 1 つのリクエストをバインドし、アプリケーションロジックを実行して、
完全なレスポンスを 1 つ書き出します。ナビゲーションとフォームは、ブラウザ標準の
セマンティクスを保ちます。

| 関心事 | 動作 |
| --- | --- |
| 処理の単位 | 1 つの `http.Handler` |
| リンク | 完全なドキュメントリクエスト |
| フォーム | 通常の送信とリダイレクト |
| 変更操作 | ハンドラまたはアプリケーションサービス |
| 変更後のブラウザ既定 | Post/Redirect/Get |
| トランザクション境界 | `pw.Transaction` による明示的な指定 |
| クライアント側の拡張 | 任意 |

このモデルが意外性に乏しいのは意図的です。Go 開発者がすでに読めるハンドラは、
フレームワークを追加しても同じように読めるままです。

## リフレクションではなく生成

馴染みのあるリクエストモデルを保っても、より強い検査を諦める必要はありません。
`pw generate` がソースを事前に読み、その隣に Go を書き出します。

| ソース | 生成されるもの |
| --- | --- |
| `*.pw.html` | 型付きコンポーネント関数とパラメータ構造体 |
| `*.pw.sql` | context を取る型付きクエリ関数 |
| `pw.Parse[T]` の呼び出し箇所 | `T` のリクエストバインディング |
| `pw.WriteAPI[T]` / `pw.NewStream[T]` の呼び出し箇所 | `T` のレスポンスエンコーディング |
| `pw.RegisterConfig[T]` の呼び出し箇所 | `T` の設定バインディング |
| 上記すべて | OpenAPI 3.1 フラグメント |

これにより、間違いが表面化する時点が変わります。URL 属性に `string` を入れた
テンプレート、SELECT の列が結果型と一致しないクエリ、新しいテンプレートパラメータを
渡し忘れたハンドラは、いずれもビルド時に失敗します。同じ生成処理がホットパスから
実行時リフレクションを取り除くため、**TinyGo** も実用的なターゲットになります。

エスケープはコンテキストに応じて自動的に行われ、生出力の抜け穴は意図的に狭く保たれて
います。ステータスとヘッダはボディの書き込み前に決まり、HTML はバッファに描画されて
検証されてから初めてコミットされます。

## レイヤー構成

生成レイヤーは、このフレームワークのために作られた
[`tinybind-go`](https://github.com/shibukawa/tinybind-go) 由来です。

| レイヤー | 責務 |
| --- | --- |
| `httpbind` | リクエストバインディング、バリデーション、JSON とストリーミング、OpenAPI |
| `htmlbind` | 型付き HTML コンポーネントとレンダーチェーン |
| `sqlbind` | 型付き SQL ステートメントと結果スキャン |
| `configbind` | 設定バインディング、スキャフォールド、サブコマンド |

Popcorn Wave はこれらを `pw` パッケージの背後にまとめるので、アプリケーションコードが
インポートするのは 4 つではなく 1 つの安定した API です。

## 標準ライブラリとの互換性

`pw.NewServeMux` は通常の Go ビルドでは `*http.ServeMux` を返します。ラッパーではなく
型エイリアスです。パターン、ワイルドカード、優先順位は完全に標準ライブラリのものです。
同じセマンティクスを持つ別実装は、標準の mux を持たない TinyGo 向けにのみコンパイル
されます。

これは全体を通じて同様です。ハンドラは `http.HandlerFunc`、ミドルウェアは
`func(http.Handler) http.Handler` であり、サーバー自体を自分で管理したい場合は
`pw.Middlewares` が素の `http.Handler` を返します。

## キャッシュ

3 つのレイヤーが独立して利用できます。

- HTTP のバリデータとレスポンスキャッシュ
- 生成された読み取りクエリの安全なキャッシュ
- アプリケーションキャッシュ

## 最小構成が除外するもの

このガイドで説明する範囲だけを使ったビルドは、小さく実用的な TinyGo ターゲットに
とどまることを目指しています。

- Popcorn Wave のブラウザランタイムなしで動作する
- 標準的なリクエストと完全なレスポンスを使う
- `net/http` のハンドラおよびミドルウェアと相互運用できる
- 型付きバインディング、設定、エラー、テンプレート、OpenAPI をサポートする
- ブラウザランタイムなしで Tailwind CSS を任意に利用できる
- コンポーネントグラフ、パッチプロトコル、ハイドレーションへの依存を含まない

最後の除外項目が境界を定めています。サーバー駆動 UI レイヤーはこの土台を拡張できますが、
土台の前提条件になることはありません。

Popcorn Wave が目指すのは、標準的な Go の常識を保ったまま生産性を上げ、なおかつ
性能の良いサービスを作れるようにすることです。アプリケーションは Go のまま読めます。
境界にあるのは `net/http` のハンドラ、`context.Context`、通常のミドルウェア、
`database/sql` です。チームがすでに知っている設計と運用の感覚を置き換えません。

この馴染みやすさは、導入した日より、その後に効いてきます。Popcorn Wave のハンドラは
標準的なミドルウェアで包めます。別の `http.Handler` と同じ mux に載せられ、テストには
`httptest` を使えます。フレームワークの採用と同時に、独自のリクエストモデルまで
コードベースへ持ち込む必要はありません。

## 生産性は、繰り返しを減らすことで上げる

Go の書き方を保つことと、機械的なコードをすべて手で書くことは別です。
`pw generate` はテンプレート、SQL、リクエストバインディング、レスポンス型、設定宣言を
型付きの Go に変換します。クエリ結果の型が変わった、テンプレートの引数を渡し忘れた。
そうした不一致は、本番のリクエストではなく、生成時かコンパイル時に止まります。

コマンドラインツールが減らすのは、もう一種類の繰り返しです。`pw init` は動く
プロジェクトを作り、`pw dev` は入力の変更を監視します。起動時バリデーション、運用
エンドポイント、グレースフルシャットダウン、構造化エラーも最初から揃います。それでも、
実体は Go のコードと設定として見えるままです。

## シンプルな実装を、裸の実装にしない

ハンドラが短いのは良いことです。ただし、認証、レスポンスポリシー、圧縮、可観測性、
設定の検査を後回しにした結果として短いのでは困ります。Popcorn Wave はそれらを標準の
経路に置き、小さなアプリケーションの周りに別のフレームワークを組まなくても使えるように
します。

- [フェデレーテッドログインとパスキー](/ja/guides/backend/authentication/)が、外部の
  アイデンティティと、フィッシングに強い再ログイン手段を提供します。
- [セキュリティレスポンスヘッダ](/ja/guides/frontend/security-headers/)は既定でブラウザの
  ポリシーを定めます。圧縮をプロキシではなくアプリケーションが担当するなら、スイッチ
  ひとつでネゴシエーション付きの[レスポンス圧縮](/ja/guides/backend/compression/)を
  有効にできます。
- 静的コード解析が、すでに書いたハンドラ、バインディング、レスポンス呼び出し、コメント
  から [OpenAPI 3.1 ドキュメント](/ja/productivity/api-documentation/)を生成します。
- [OpenTelemetry 連携](/ja/guides/architecture/telemetry/#リクエストトレースを読む)が構造化ログとトレースを送出し、
  フレームワークのスパンが、アプリケーション固有のタイマーを書かずに、リクエスト、
  レンダリング、データベース処理を見えるようにします。
- 型付きの[設定](/ja/guides/architecture/configuration/)は環境変数を受け取り、
  [`pw doctor`](/ja/pw/project/doctor/)は指定した環境での最終的な設定を解決して、欠落、
  矛盾、危険な値をデプロイ前に報告します。

圧縮をプロキシに任せるか、どの IdP を信頼するかといった判断まで、フレームワークが
奪うわけではありません。変わるのは出発点です。素直に実装するだけで、安全性、通信性能、
可観測性、そして開発・運用の使い勝手が自然に引き上げられます。

JavaScript のエコシステムは生産性に貪欲で、Go のエコシステムは安定性を大切にして
きました。Popcorn Wave が目指すのは、その中間ではありません。Go の安定した境界と
予測しやすい運用を保ったまま両者の距離を詰め、その先では JavaScript 界隈が築いた
生産性の水準を追い越すことです。生成による検査、安全な既定値、統合されたツールまで
含め、Go で作る経路そのものを、より生産的な選択にします。

## 生産性のための仕組みが、実行時の性能にも効く

コード生成は、仕事をリクエスト処理の外へ移します。テンプレートは型付き関数を呼び、
生成されたバインダは既知のフィールドへデコードし、クエリは既知の列をスキャンします。
リクエストのたびにリフレクションで構造を調べ直す必要はありません。ブラウザ側の追加機能も
別の import なので、使わないサービスがそのランタイムを抱えることはありません。

それが一番はっきり出るのは描画です。同じ在庫テーブルを二通りに書き、片方は起動時に
パースした `html/template`、もう片方は型付きコンポーネント。出力は同じバイト列です。
Go 1.26.5、Apple M3 で 15 回実行した中央値です。

| 行数 | `html/template` | 生成コード |
| --- | --- | --- |
| 1 | 2.55 µs · 1032 B · 41 allocs | 393 ns · 560 B · 5 allocs |
| 50 | 78.5 µs · 26.1 KiB · 1282 allocs | 6.82 µs · 611 B · 21 allocs |
| 500 | 780 µs · 259 KiB · 12 956 allocs | 70.4 µs · 2.14 KiB · 472 allocs |

効き方が積み上がるのはメモリの列です。50 行のページが 26 KiB ではなく 611 バイト。
確保しなかったものは後で回収する必要もありません。回収のコストは、たまたま走っている
別のリクエストが払わされるものです。生成された JSON コーデックも、規模は小さいながら
同じ形をしています。6 フィールドのリクエストのデコードが 998 ns に対して 184 ns、
エンコードが 160 ns に対して 74 ns。ただし HTTP リクエスト 1 本の中では、この差は
リクエスト自体のコストにほぼ埋もれます。

土台は `net/http` です。サーバー、ツール、ミドルウェアの慣習、プロファイリング手段まで、
Go のエコシステムにすでにあります。多くのサービスに十分な性能を得ながら、必要になるか
わからないベンチマーク上の差のために相互運用性を手放さない。これが Popcorn Wave の
標準的な選択です。

## TinyGo を第一級の対象にする

リフレクションを外したことには、もうひとつの帰結があります。そしてこのプロジェクトが
賭けているのはそちらです。WebAssembly がサーバーサイドの配置先として当たり前になるなら、
そこへ到達するコンパイラは TinyGo です。そして `html/template` は、TinyGo では動きません。
コンパイルは通り、パッケージ初期化の途中で、TinyGo が実装していないリフレクションに
当たって panic します。1 バイトも描画される前です。生成コンポーネントには調べるべき
リフレクションがないので、そのまま動きます。

Go のサーバーが手に取るものの多くが同じ問題を抱えています。`crypto/tls`、Go 1.22 の
`ServeMux`、`aws-sdk-go-v2`、Google のクライアントライブラリ。TinyGo を機能制限モードと
扱う代わりに、依存を作り直しました。
[`tinygodriver`](https://github.com/shibukawa/tinygodriver) が、ホストのネットワーク
ドライバ、OS の TLS スタックを使う HTTPS、SQLite・PostgreSQL・MySQL の `database/sql`
ドライバ、S3・DynamoDB・Datastore のクライアントを提供します。ひとりで背負う量としては
正気ではなく、AI の支援があって初めて現実的になりました。

## HTTP スタック自体がボトルネックになったら

`net/http` より高い性能が必要なサービスもあります。計測の結果、HTTP スタック自体が
限界だと分かったなら、`fasthttp` はその要件のために設計された有力な選択肢です。
ただし、リクエスト API とエコシステムの境界が異なります。Popcorn Wave は、その上に
`net/http` 風の互換レイヤーを載せる設計にはしていません。

これは `fasthttp` の評価ではなく、担当する範囲の違いです。Popcorn Wave は、標準的な
Go との互換性、開発速度、生成による強い検査を同時に必要とする領域を最適化します。
計測によって別の境界が必要だと分かったサービスは、その要件に合う境界を選べます。

import { Card, CardGrid } from '@astrojs/starlight/components';

Popcorn Wave は、標準的な Go の常識を保ったまま生産性を上げ、性能の良いサービスを
作れるようにします。出発点は、Go がすでに提供している処理単位、1 つの
`http.Handler` です。リクエストを
バインドし、アプリケーションロジックを実行し、通常のナビゲーションとフォームの
セマンティクスで完全なレスポンスを書き出します。その結果は、小さく実用的な TinyGo
ターゲットのままです。コンポーネントグラフ、パッチプロトコル、ハイドレーション、
ブラウザランタイムはいずれも含まれません。

<CardGrid>
  <Card title="標準ライブラリ優先" icon="seti:go">
    ルーティングには `net/http` の `ServeMux` そのものを使います。パターン、
    ワイルドカード、優先順位は同じで、ハンドラも素の `http.HandlerFunc` のままです。
  </Card>
  <Card title="リフレクションではなく生成" icon="setting">
    `pw generate` がテンプレート、SQL、リクエストバインディング、OpenAPI を事前に
    Go へコンパイルします。実行時リフレクションがないため、同じコードを
    **TinyGo** でも実行できます。
  </Card>
  <Card title="1 コマンドで動くアプリ" icon="rocket">
    `pw init` がハンドラ、型付きページ、ドキュメントシェル、SQL、マイグレーション、
    エラーページ、Devbox まで含む完全なプロジェクトを作り、`pw dev` が監視します。
  </Card>
  <Card title="運用機能を同梱" icon="approve-check">
    起動時バリデーション、`/healthz`、`/readyz`、`/openapi.json`、グレースフルシャット
    ダウン、リクエスト ID、アクセスログ、検証済みセキュリティヘッダ。
  </Card>
</CardGrid>

後からより高度なインタラクションが必要になっても、オプトインのサーバー駆動 UI
レイヤーが同じ `net/http` の土台を置き換えずに拡張します。アプリケーションがその
レイヤーをインポートしなければ、コストも発生しません。

[なぜ Popcorn Wave なのか](/ja/start/why-popcorn-wave/)では、生産性、性能、相互運用性が
この選択によってどう結び付くのかを説明します。

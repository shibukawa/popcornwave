遅いページには形があります。所要時間だけでは、その形は見えません。`842ms`
はリクエストが遅かったことしか語らない。シェルに 800ms かかって非同期境界が
40ms だったのか、シェルが 40ms で境界の中の1本のクエリが 800ms だったのか。
この2つは正反対の直し方を要求しますが、どちらを見ているのかをフレームワークが
言わないかぎり、確かめる方法は計測コードを足すことしかありません。

そこで、スパンはフレームワーク自身が開きます。トレースされたリクエストは木と
して届きます。

```
GET /orders                                      842ms
└─ render stream                                 838ms
   ├─ render initial                              41ms
   │  └─ SELECT                                   33ms
   ├─ render boundary  (tb-1)                    797ms
   └─ render boundary  (tb-2)                    120ms
```

シェルは速かった。1秒近くフォールバックを表示し続けた境界がひとつあり、それは
`tb-2` ではなく `tb-1` のほうだった。診断はこれで終わりで、そのために
アプリケーション側に計測を入れる必要はありません。

## 有効にする

[`pw dev`](/ja/productivity/dev-telemetry-viewer/) で動かしているなら、
何もしなくて構いません。開発ループはアプリケーションをローカルのレシーバへ
向けますし、既定値はそれに追従します。

```toml
[observability.trace]
enabled = "auto"   # トレースを送出しているときは on、していないときは off
```

`auto` は慎重な既定値ではなく、正直な既定値です。スパンはアロケーション1回、
タイムスタンプ2つ、そして送出のコストを払います。送り先を持たないプロセスは、
その3つを払ったうえで記録を捨てることになる。OTLP のエンドポイントを書くこと
自体が送出を有効にし
（[`[observability.otel]`](/ja/reference/configuration/#observabilityotel)）、
同じ行為がこれらのスパンも有効にします。

自分でトレーサプロバイダを持っていて、エンドポイント設定に関わらず木がほしい
場合は `enabled = "on"` にします。逆に、1リクエストあたり数個のスパンでも許容
できないほどホットな経路だと実測でわかっているなら `"off"` です。

## レンダースパン

HTML レスポンスはひとつスパンを開き、その名前がレスポンスの取った6つの分岐の
どれかを言います。この名前は見た目以上の価値があります。どの分岐を通ったかは、
しばしばそれ自体が驚きだからです。

| 名前 | レスポンスの正体 |
| --- | --- |
| `render buffered` | 最初の1バイトの前にドキュメント全体を組み立てた |
| `render stream` | [非同期レンダリング](/ja/guides/cross-layer/async-rendering/)。シェルが先、境界が後 |
| `render live` | ドキュメントではなく[ライブ](/ja/guides/cross-layer/live-rendering/)配信ストリーム |
| `render navigate` | [ナビゲーション差分](/ja/guides/cross-layer/partial-updates/) |
| `render redraw` | 1つのコンポーネントが自分で答えた |
| `render fragment` | 外部のスワップライブラリ向けの素のフラグメント |

ストリーミングのつもりで書いたページが `render buffered` で届いたなら、
クローラと分類されたか、`html.streaming` を切って動いているかのどちらかです。
どちらもレスポンスボディからは見えません——バイト列はどちらの場合も完全で正しい
ドキュメントです——が、どちらも見ている数字の意味を変えます。属性がそれを言い
ます。`pw.render.bot` が分類の結果を、`pw.render.async` と `pw.render.live` が
合成されたチェーンの実際の中身を持ちます。

このスパンは `pw.render.bytes`（クライアントに届いた非圧縮のバイト数）と
`pw.render.boundaries`（確定した領域の数）も運びます。

[レンダリングキャッシュ](/ja/guides/frontend/rendering-cache/)に問い合わせた
レスポンスは、これに `pw.render.cache_hits` と `pw.render.cache_misses` を足し
ます。ストアに届かなかったレスポンスはどちらも持ちません。両方を出すのは、
ヒット数だけでは「効いているキャッシュ」と「ほとんど誰も届かないキャッシュ」を
見分けられないからです。そして、作者が当てずっぽうで書いた TTL を検算するもの
は、システムのどこにもありません。呼び出しごとにパラメータが変わるコンポーネント
は、キーとバッファの代金を払いながら、キャッシュなしとまったく同じように描画し
ます。それを言うのがこの2つです。

## 初回表示が終わる場所

ストリーミングレンダリングの中では、子スパンがひとつ初回ビルドを覆います。
ドキュメントシェル、マージされた head、そしてすべてのフォールバック。この
スパンはドキュメントをコミットするフラッシュで終わります。訪問者が最初に何かを
目にする瞬間です。

この時刻が、木の残りを読めるものにします。各境界スパンはそこから始まり、
フラグメントが書かれた時点で終わる。つまりその長さは、そのフォールバックが
画面に居座った時間そのものです。境界自身の処理にかかった時間ではありません。
[`html.async_concurrency`](/ja/reference/configuration/#html) の後ろで待った境界
は、そのスパンの一部を順番待ちで過ごしています。この差は、クエリを速くするのか
上限を上げるのかを決める場面で効いてきます。スパンが測るのは訪問者の体験で、
処理の中で [`pw.StartSpan`](/ja/reference/runtime/#トレーシング) を呼んで開くスパンが
測るのが処理そのものです。

ライブレスポンスは、同じ考え方をもっと長い時計の上でやります。各配信スパンは
その境界の前回の配信から始まるので、連続するスパンは隣接し、ウォーターフォール
は点の散らばりではなく「ひとつの領域が変わり続けている」ものとして読めます。
レンダースパンは `pw.live.close_reason` を持って閉じ、ソースが終わったなら
`done`、健全なストリームを[購読の上限](/ja/guides/cross-layer/live-rendering/)
が閉じたなら `retry` になります。

バッファ済みレスポンスとフラグメントレスポンスは、初回ビルドの子を開きません。
その分岐には初回パスの後に何もないので、親とまったく同じ範囲を持つ2つめの
スパンは同じことを二度言うだけです。

## その下で走った文

`.pw.sql` から生成された関数は、すべてフレームワーク内の1か所でハンドルを解決
します——[クエリ診断](/ja/productivity/query-diagnostics/)が使うのと同じ継ぎ目
です——ので、各文はキーワードを名前に持つクライアントスパンになります。

```
├─ render boundary  (tb-1)                       797ms
   └─ SELECT                                     791ms
      db.system.name    = postgresql
      db.operation.name = SELECT
      db.query.text     = SELECT * FROM orders WHERE customer = $1
      pw.db.slow        = true
```

文のテキストはスパンに載りますが、バインド値は載りません。載せる設定もありま
せん。トレースのバックエンドはアプリケーションログより長く保持され、より広く
読まれる。だから行データはクエリレコードのほうに残ります。そしてそのレコードは
リクエストのルートではなくこのスパンを名指すので、トレース上の1行から値へも
プランへも[再実行スニペット](/ja/productivity/query-diagnostics/)へも辿れます。
検索ではなく、1クリックです。

`pw.db.slow` は文が `observability.query.slow_threshold` を超えたときに現れ
ます。ウォーターフォールとログが出会う場所がここで、どのレコードを開けばよいか
をスパンが教えます。

## 何を切るか

親の下には3つのキーがあり、それぞれ別の不満に答えます。

```toml
[observability.trace]
enabled = "auto"
render = true      # レスポンスのスパンと、その中身すべて
boundary = true    # 確定した境界ごと、ライブ配信ごとのスパン
database = true    # 文ごとのクライアントスパン
statement = true   # そのスパンに載る SQL テキスト
```

小さな領域を多数持つページや、毎秒配信するライブ画面でまず手を伸ばすのは
`boundary = false` です。長生きするレスポンスは、放っておくと同じことを言う
スパンを数百個生みます。数え上げは `pw.render.boundaries` として残ります。
スパンではなく属性だからです。

`statement = false` は時間だけを残して SQL を落とします。切るべきなのは、文が
長くてテキストが送出量を支配するときであって、内容への警戒からではありません。
そこに載るのは `.pw.sql` が持っているパラメータ化された形そのままで、値は入って
いません。

クエリログを切らずに `database = false` にするのは逆の組み合わせで、データベース
プロキシ経由ですでにコレクタが文を見ている場合にはこれが正しい形です。

何も開かない設定は、そもそもポリシーとして構築されません。だから親を切ったとき
のコストは、レスポンスごと・文ごとの比較1回だけです。ライタもエグゼキュータも
包まれず、スパンオブジェクトはどこにも作られません。

## どこで止まるか

フレームワークのスパンが覆うのはフレームワークの仕事です。ハンドラ自身の呼び出し
——他サービスへの HTTP リクエスト、キャッシュ参照、レンダリング開始前に
[`pw.Go`](/ja/guides/cross-layer/async-rendering/) で始めた処理——を開くのは
あなたの仕事で、[`pw.StartSpan`](/ja/reference/runtime/#トレーシング) を使えば呼んだ
時点でアクティブなスパンの下に入ります。

見つけて驚くより先に知っておく価値のある穴が2つあります。フレームワークが自分
のために発行する文——セッション、認証、マイグレーションの SQL——はプールへ直接
行き、スパンを作りません。クエリログが適用しているのと同じ除外です。もうひとつ、
`render navigate` と `render redraw` のスパンは中の領域ごとではなく呼び出し全体
を覆います。どの領域を送るかを決める比較が、フレームワーク自身のコードより下で
起きているからです。

キーの一覧は
[`[observability.trace]`](/ja/reference/configuration/#observabilitytrace) に、
何もインストールせずに結果を読む方法は[開発用テレメトリビューア](/ja/productivity/dev-telemetry-viewer/)にあります。

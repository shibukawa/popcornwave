セッションの設定は、ひとつに見えて2つの判断です。レコードをどこに置くか、
どれだけ有効にするか。どちらも設定ファイルの話であって、ハンドラには届きません。
[`session.Read`](/ja/guides/backend/sessions/) も `auth.User` も、レコードがクッキーの中に
あろうと、データベースの行にあろうと、Redis や DynamoDB にあろうと、同じものを返します。

ブラウザが持つものも変わりません。クッキーが運ぶのは 256 ビットのランダム値だけで、
ストアの鍵はその SHA-256 ハッシュです。バックエンドのダンプが漏れても、そのままでは
クッキーとして再生できません。レコード自体までブラウザに置くバックエンドは1つだけで、
それも封をしてから置きます。

## 有効にする

```toml
[session]
enabled = true
backend = "rdb"
ttl = "12h"
idle_timeout = "1h"
cookie.secure = true
```

```go
// cmd/myapp/main.go — ストレージはオプトインなので、バックエンドは import でもあります。
import _ "github.com/shibukawa/popcornwave/sessionstore/sqlite"
```

よくある間違いは1つ、import を書かずにバックエンドだけ設定することです。エラーが直し方を
そのまま出します。

```
session.backend = "rdb" needs its plugin; add to the application:
import _ "github.com/shibukawa/popcornwave/sessionstore/sqlite"
```

例外は `cookie` で、何も保存しないので何も import しません。置き場所を用意する前から
セッションが動くプロジェクトになります。

## どのバックエンドでも読まれる設定

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `enabled` | `false` | true のときだけミドルウェアが動く |
| `backend` | `"rdb"` | `rdb`、`cookie`、`redis`、`dynamo` |
| `ttl` | `"24h"` | 絶対寿命。操作の有無にかかわらずここで終わる |
| `idle_timeout` | `"0s"` | 無操作での寿命。ゼロで無効 |
| `renewal_interval` | `"0s"` | 無操作期限を延ばす最小間隔。ゼロなら `idle_timeout` の 1/10 |
| `cookie.name` | `"pw_session"` | |
| `cookie.path` | `"/"` | ルートから始まること |
| `cookie.domain` | *(空)* | 空ならホスト限定。そちらが安全側 |
| `cookie.secure` | `true` | 落としてよいのはループバックの開発時だけ |
| `cookie.http_only` | `true` | |
| `cookie.same_site` | `"lax"` | `strict` / `lax` / `none`。`none` は `secure` なしだと起動時に拒否 |

`ttl` は正の値で最大1年、`idle_timeout` はそれを超えられません。どちらも最初の
リクエストより前に検証されるので、矛盾した設定は「知らないうちにセッションが短い」
ではなく起動失敗になります。

調整する前に理解しておく価値があるのは更新の挙動です。アクティブなリクエストは無操作
期限を延ばしますが、毎回ではありません。最後に見た時刻から `renewal_interval` が過ぎて
初めてストアに触り、絶対期限を超えることはありません。ゼロのままなら、無操作期限1時間の
設定でセッションあたり最大6分に1回の書き込みです。短くすれば精度は上がり、書き込みは
増えます。

ログイン時にはトークンが更新されます。新しいレコードを発行する前に古いものを失効させる
ので、認証前に盗まれたトークンは認証後には使えません。セッション固定攻撃は、それが問題に
なる地点で閉じてあります。

## 4つのバックエンド

### rdb — セッションごとに1行

既定です。`middleware.rdb.enabled = true`、テーブルを作るマイグレーション、そして動かす
エンジンの import が要ります。[リレーショナルデータベース](/ja/guides/storage/rdb/)を参照。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `rdb.source` | `"middleware"` | `middleware.rdb` のプールを再利用。`dedicated` は未実装 |
| `rdb.group` | *(空)* | テーブルを持つ接続グループ。空なら `middleware.rdb.write_group` |
| `rdb.table` | `"popcornwave_session"` | |

SQLite・PostgreSQL・MySQL のいずれでも動き、パッケージはエンジンごとです
（`sessionstore/sqlite`、`sessionstore/postgres`、`sessionstore/mysql`）。マイグレーションの
方言も同じくエンジンごとです。`pw init` は選んだエンジンの import とマイグレーションを
書き出し、`pw add auth` は import を手作業ステップとして表示してマイグレーションを書きます。

起動時にテーブルは作られず、検証されます。マイグレーションを忘れたデプロイには、適用すべき
ものが名指しで返ります。

```
sessionstore: session table is missing: apply the migration named
init_popcornwave_session with pw migrate up
```

ログアウトされずに放置されたセッションは行として残るので、auth プラグインが10分ごとに
期限切れを掃除します。

### cookie — ストレージなし

レコードは AES-256-GCM で封をされ、トークンの隣の2つ目のクッキーで運ばれます。封は
そのトークンのハッシュに結びついています。サーバーには何も残らないので、マイグレーションも
掃除もネットワーク越しの到達先も要りません。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `cookie_store.secret` | *(空)* | **必須**。32 バイト以上のランダム値を base64 で |
| `cookie_store.name` | `"pw_session_data"` | 封をしたレコードを運ぶクッキー |
| `cookie_store.previous_secrets` | `[]` | 引退した鍵。読み出しには通る |

鍵は一度作って、ファイルの外に置きます。

```bash
export SESSION_COOKIE_SECRET=$(openssl rand -base64 32)
```

```toml
[session.cookie_store]
secret = "${SESSION_COOKIE_SECRET}"
```

`previous_secrets` があるのはローテーションのためです。新しい鍵が書き、古い鍵はまだ読める
ので、レコードを持っているブラウザは期限までセッションを保てます。古い鍵をリストから外せば、
それで書かれたレコードは一斉に受け付けられなくなります。

この最後のレバーは、ほかのバックエンドより重要です。**このバックエンドは個別のセッションを
失効させられません**。ログアウトはクライアントのコピーを消しますが、その前に取られたコピーは
封の中の期限まで有効です。消すべきサーバー側レコードが存在しないからです。`ttl` を短くすれば
窓は狭まり、鍵のローテーションは未回収のセッションを一斉に終わらせます。「特定の1セッションを
今すぐ切りたい」なら、これは選ぶべきバックエンドではありません。

もうひとつの限界はサイズです。ブラウザはおよそ 4 KB を超えるクッキーを黙って捨てるので、
ストアは書く前に断ります。`session.ErrCookieTooLarge` を書き込み時に返す、という形です。
「なぜかセッションが始まらない」に化けません。

### redis — 期限はサーバーが持つ

Redis と Valkey の両方で動き、使うのは `GET`、`SET`、`SET XX`、`DEL` だけです。各レコードは
自分の期限から計算した TTL 付きで書かれるので、放置されたセッションは勝手に消え、掃除の
スケジュールは存在しません。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `redis.dsn` | *(空)* | **必須**。`redis://` または `rediss://` |
| `redis.key_prefix` | `"pw:session:"` | このストアが所有する鍵空間 |
| `redis.connect_timeout` | `"5s"` | 起動時の ping と各コマンドの期限 |

```toml
[session]
backend = "redis"

[session.redis]
dsn = "redis://${REDIS_HOST}:6379/0"
```

起動時にサーバーへ接続して ping します。応答がなければ最初のログインで失敗するのではなく、
デプロイが止まります。鍵は設定したプレフィックスの外に出ず、ストアはスキャンも列挙もしません。

ループバックの外では、TinyGo の直接 TLS ではなくローカル TLS プロキシ経由で到達してください。

### dynamo — リレーショナルデータベースを持たない

すでに DynamoDB に課金しているデプロイが、テーブル 1 つのためにリレーショナルデータベースを
増やす必要はありません。このバックエンドはその場合のものです。
[`database/dynamo`](/ja/guides/storage/dynamodb/) が開いたクライアントを借りる——つまりその
パッケージが有効かつ import 済みである必要がある——ので、自分では何も開きません。

```go
import (
	_ "github.com/shibukawa/popcornwave/database/dynamo"
	_ "github.com/shibukawa/popcornwave/sessionstore/dynamo"
)
```

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `dynamo.table` | `"popcornwave_session"` | 宣言上のテーブル名。実際の名前へは `middleware.dynamo` が対応づける |
| `dynamo.consistent_read` | `false` | 最初の読み取りを強整合にする |

テーブルのキーは属性1つ——セッショントークンのハッシュ——で、ソートキーはありません。
import が定義を登録するので、`middleware.dynamo` が開発では他のテーブルと一緒に作り、
どの環境でも起動時に検証します。

読み取りは既定で結果整合です。値段が半分になり、認証済みリクエストのほぼ毎回で読むストア
では、その値段こそが設計になります。代わりに買う危険は狭く、そして実在します。ログインは
トークンを更新し、ブラウザはリダイレクトをたどり、次のリクエストがまだ追いついていない
レプリカに当たる——ログインした瞬間にログアウトして見えます。そこで、何も見つからなかった
読み取りは 1 回だけ強整合で読み直し、その答えを最終とします。見つかった場合に読み直すことは
ないので、通常のリクエストは安い読み取りのままで、2 回目を払うのは、どのみち拒否される
リクエストだけです。`consistent_read = true` にすると最初から強整合になり、この再試行は
なくなります。

**期限切れレコードを消すものは、ここには何もありません。** 正しさは削除に依存しません。
期限を過ぎたレコードは「見つからない」として扱われ、`Touch` は生きていることを条件にするので、
更新が蘇生させることもありません。残るのはバイト列のほうです。ストアは先に来るほうの期限を
`dead_at` 属性に維持します。実際に消すのはその属性を指した DynamoDB の TTL で、有効にするのは
テーブルを用意した側であり、ここにあるものではありません。TTL がなければテーブルは無限に
育ちます。

代わりの掃除は用意していません。これは意図的です。ここでの掃除は `Scan` であり、100 万件の
期限切れセッションを消すのに 100 万件の読み取りを払うことになります。TTL ならそれが無料です。
rdb のバックエンドが掃除をするのは、あちらでは同じ仕事が `DELETE` 1 文で安く済むからです。

DynamoDB のアイテム上限を超えるレコードは、送信前に上限を名指しして拒否されます。

## 選ぶ

| | cookie | rdb | redis | dynamo |
| --- | --- | --- | --- | --- |
| 運用するストレージ | なし | すでにあるテーブル | もう1つのサービス | すでにあるテーブル |
| 個別セッションの失効 | 不可 | 可 | 可 | 可 |
| ペイロードのサイズ | 約 4 KB（強制） | 行のサイズ | レコードのサイズ | 400 KB（強制） |
| 放置されたものを回収するのは | 誰でもない。スタンプが切れる | 定期的な掃除 | サーバーの TTL | テーブルの TTL（有効にしていれば） |
| import | なし | `sessionstore/<engine>` | `sessionstore/redis` | `database/dynamo` と `sessionstore/dynamo` |

この表は結局ひとつの問いです。自分が始めたのではないセッションを終わらせる必要があるか。
クッキーセッションの答えは「ない」で、それ以外の性質はすべてそこから導かれます。答えが
「ある」なら、あとはレコードを安く置ける場所——すでに動かしているデータベースか、期限を
勝手に切ってくれるサーバーか——の選択になります。

あとから変えるのは設定1行と import 1行です。ただし発行済みのセッションは移行しません。
ユーザーはログインし直します。デプロイの後ではなく前に決めておく価値がある、というのは
そういう意味です。

ハンドラからレコードを読む方法は、どのバックエンドでも同じ呼び出しです。
[セッション](/ja/guides/backend/sessions/)を参照してください。

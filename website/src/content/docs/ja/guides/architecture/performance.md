Popcorn Wave のサービスを手書きの `net/http` と比べた結果は、ほぼ 1 つの設定で
決まります。[`examples/todo`](https://github.com/shibukawa/popcornwave/tree/main/examples/todo)
の 2 つ（PostgreSQL のテーブル 1 つ、同じ 5 ルート）では、**同じコードのまま**
cookie セッションだと 18% 後ろ、サーバー側セッションだとむしろ前に出ます。

| セッションバックエンド | スループット（対ベースライン） | HTML p95 | 1 レスポンスの `Set-Cookie` |
| --- | --- | --- | --- |
| `cookie` | −18% | 3.76〜4.07 ms | 631 B |
| `dev-volatile` | +2.7% | 2.80〜2.99 ms | 299 B |

ベースラインの HTML p95 は 3.49〜3.95 ms なので、サーバー側構成は
スループットが同等で、しかも最初のバイトまでが約 20% 速い。

この数字はアイドル状態のマシンでの 1 セッション分です。後日、混んだマシンで
測り直したときはベースラインが約 13,900 ではなく 11,400〜11,700 になりましたが、
**同じ 2 つの比**（cookie で −14%、サーバー側で同等）が再現しました。
読むべきは比のほうで、絶対値は測ったマシンのものです。

このページは可能なかぎりパーセントではなくマイクロ秒で書いています。
パーセントは測ったワークロードでしか成り立たないからです。「セッションは
CPU の 0.8%」はクエリを 1 本足した瞬間に別の数字になり、しかも**自分の
リクエスト予算に足せない**。マイクロ秒なら足せます。

## リクエストの各部分のコスト

todo サービスに 20 並列で負荷をかけ、1 リクエストあたりに割り当てた CPU 時間です。
Go 1.26.5、Apple M3、PostgreSQL 17 は同一マシンの Docker。

| 1 リクエストあたり | CPU |
| --- | --- |
| セキュリティヘッダ | 0.2 µs |
| リクエスト ID、リカバリ、ボディ上限、運用エンドポイント | 0.5 µs |
| セッションミドルウェア（cookie バックエンド） | 1.5 µs |
| CSRF チェック | 2.4 µs |
| **ミドルウェア鎖 全体** | **4.5 µs** |
| 50 行を返す `SELECT` 1 本 | 49 µs |
| HTML ページの描画と書き出し | 102 µs |
| JSON レスポンスの符号化と書き出し | 41 µs |

フレームワークのリクエストごとの帳簿付けは全部で **4.5 µs**。ループバック上の
暖まったプールに対するクエリ 1 本が **49 µs** で、**11 倍**です。ネットワークを
越えて実際のデータベースに行くクエリなら数百 µs からミリ秒の世界で、そこに
対してこの鎖は見えません。

正直な形はこうです。フレームワークのオーバーヘッドは実在し、固定で、小さく、
**アプリケーションの規模とともに増えない**。一方、規模とともに増えるものは
すべて別の場所にあります。

この表は「1 行での大勝ちが全体では小勝ち」になる理由も説明します。PostgreSQL
接続はリクエスト時のクエリを `database/sql` 経由ではなく pgx ネイティブプールで
実行するようになり、フレームワーク側のベンチマークでは **34.9 µs/op・15 allocs
から 23.0 µs/op・8 allocs** へ、クエリの 3 分の 1 が落ちました。ところが HTTP
レベルの比は数ポイントしか動かず、実行ごとのばらつきの内側です。クエリは上の表の
1 行でしかなく、リクエストは表の全部だからです。**どちらの主張も正しく、
誤解を招く形で引用されがちなのは per-op のほう**です。

## cookie セッションは実際いくらか

暗号化するぶん高いだろうと思われるのがセッションです。単独で値段をつけて
おきます。

todo サービスの封をしたセッション cookie のペイロードは 215 バイト。
`Keyring.seal` と `Keyring.open` を直接計測（AES-GCM、各 10 回）:

| ペイロード | seal | open |
| --- | --- | --- |
| 64 B | 357 ns | 120 ns |
| 256 B | 373 ns | 122 ns |
| 1 KB | 576 ns | 265 ns |
| 3 KB | 1.07 µs | 589 ns |

1 リクエストは入ってきた cookie を開き、出ていく cookie を封じるので、
典型的なセッションの暗号処理は**往復で約 0.5 µs**。ブラウザの上限に近い
3 KB でも 1.7 µs です。封ではなく署名のスロットなら HMAC で、署名 393 ns、
検証 410 ns。

0.5 µs はループバックのクエリ 1 本の 100 分の 1 なので、**冒頭の 18% が
暗号化のせいということはあり得ません**。cookie の代金は CPU ではなく
**バイト数**です。cookie バックエンドのレスポンスは `Set-Cookie` ヘッダを
631 バイト運びます。サーバー側セッションなら 299 バイト。レコード本体が
travel するからです。そしてブラウザはそれを以降の毎リクエストで送り返します。
帯域、ヘッダ解析、そしてパケットを 1 つ余計に使う可能性が、往復のたびに乗る。

実務的な読み方はこうです。セッションがスループットを食っているなら、
**暗号を速くしようとせず、レコードをサーバー側へ移してください。**
ここに最適化する価値のある暗号処理はありません。

再現:

```sh
go test ./session/ -bench Keyring -benchmem -count=10
```

## 単純なベンチマークがベースラインを有利にする 3 点

**いちばん大きいのはコードではなく設定です。** スキャフォールドの
`config.dev.toml` は debug で記録し、データベースが実行する文をすべて出します。
todo サービスではこれだけで **毎秒 3,425 と 8,700 リクエストの差**。自分の仕事を
説明するほうに時間を使っている状態です。このページで唯一「1 リクエストあたりの
CPU」ではない数字ですが、それでも他の全部を足したより大きい。結論を出す前に
本番相当の設定（`examples/todo/popcornwave/config.bench.toml`）を指してください。

**そもそも同じ仕事をしていません。** フレームワーク側のリクエストはどれも
セッション、CSRF チェック、セキュリティヘッダ、リクエスト ID を伴い、描画される
フォームはトークンを持ちます。手書き版にあるのはヘッダを 1 つ付けるミドルウェア
だけ。HTML は 14 KB 対 27 KB で、差は 100 個のフォームの CSRF トークンです。
それをベースラインに手で足す作業こそフレームワークが取り除くためのものなので、
省いたベンチマークは機能の不在を測っています。

**スループットとレイテンシは別の問いです。** 毎秒リクエスト数で 18% 負けている
cookie 構成でさえ、HTML の p95 は **3.76〜4.07 ms 対 3.69〜3.95 ms** で実質同等。
サーバー側セッションなら 20% 前に出ます。レイテンシが同じでスループットが低いのは、1 リクエストが遅いの
ではなくコアを埋めきれていないということ。1 リクエストあたり CPU も同じで
**254 µs 対 244 µs**、4% 差。しかもスループットが 34% 振れたパスをまたいでも
この比は動きませんでした。ユーザーが感じるのがレイテンシなら、測るのは
レイテンシです。

## 本番でチューニングすべきところ

5 つ、報われる順に。

### まずセッションバックエンド

単独で最大のレバーです。証拠は冒頭の表で、同じコードのまま 18% 開きます。
cookie セッションはレコード全体を毎リクエスト 2 回線に載せ、サーバー側セッションは
識別子だけを送ってレコードはバイト代のかからない場所に置きます。

```toml
[session]
enabled = true
backend = "rdb"   # または redis, dynamo, firestore
```

冒頭の計測で使った `dev-volatile` は**開発専用**です。再起動で全セッションが
消えるため、フレームワークは開発環境以外で拒否します。本番で同じ形になるのは
`rdb`、`redis`、`dynamo`、`firestore`。どれも小さな識別子 cookie だけを送りますが、
**cookie バックエンドにはないストレージ往復が毎リクエスト増えます**。つまり
「毎リクエストのバイト」と「毎リクエストの参照」を交換しているだけで、
どちらが得かはストレージのレイテンシ次第。思い込まずに測ってください。
差が問題になる場面では `redis` が定番の答えです。

置き場所がない場合、あるいはセッションが小さくて依存を増やしたくない場合は
`cookie` のままで構いません。[セッション](/ja/guides/backend/sessions/)に
永続性と失効の違いがあり、性能より先にそちらで決まることがほとんどです。

### 次にコネクションプール

`pw init` は 10 本でスキャフォールドします。実運用には小さい値です。

```toml
[[middleware.rdb.connections]]
group = "default"
max_open_conns = 25
max_idle_conns = 25
```

todo サービスでの実測では 10 → 25 で **+8.5%**、50 は 25 より遅くなりました。
万能の数字はありません。上限は「動かす全インスタンスの合計をデータベースが
受けられるか」で決まり、それを超えると増やしたぶんはサーバー側の競合になります。
25 から始めて計測し、PostgreSQL が耐えられるか問う前に**レプリカ数を掛けて**
ください。

`max_idle_conns` は理由がなければ `max_open_conns` と同じ値に。アイドル数が
少ないと負荷変動のたびに接続が閉じて開き直され、再接続ごとの TLS ハンドシェイクは
アイドルソケット 1 本よりはるかに高くつきます。

### 3 番目にログ

本番の既定はすでに正しく（`minimum_level` は info、クエリログは dev 以外で off）、
やることは「上書きしないこと」だけです。何かを追うために文のログを on にしたなら
戻してください。[クエリ診断](/ja/productivity/query-diagnostics/)を参照。

### 4 番目に圧縮

既定は off で、たいていそれが正解です。手前にいる何かがすでに圧縮しているから。
そうでない場合の条件は[レスポンス圧縮](/ja/guides/frontend/compression/)に
あります。

### 最後に CSRF の範囲

2.4 µs は鎖の中で最も高い項目ですが、鎖全体が 4.5 µs なので、よほど確信が
ない限り誤差です。しかもトークンが発行されるのは HTML ドキュメントらしき
リクエスト（`Accept: text/html` または `Sec-Fetch-Dest: document`）だけなので、
API の読み取りは設定なしですでにこの処理を飛ばしています。逆に言うと、
これらのヘッダを送らない負荷ツールはページ経路を測っておらず、
フォームの描画がトークン不足で失敗します。`include` の既定は全パス。ベアラトークンで認証しセッションを
持たない API には不要です。

```toml
[security.csrf]
enabled = true
include = ["/**"]
exclude = ["/api/**"]
```

除外するのは、**ブラウザからクッキー付きで叩かれ得ないことが確実なパスだけ**に
してください。間違えれば、2.4 µs と引き換えにチェックが存在する理由の脆弱性が
戻ってきます。

## それでも足りないとき

プロファイルの結果 HTTP スタック自体が限界だと分かったなら、`fasthttp` は
そのために設計されたもので、Popcorn Wave はそこと競っていません。
[なぜ Popcorn Wave なのか](/ja/start/why-popcorn-wave/#http-スタック自体がボトルネックになったら)を
参照。その境界を越えるのは `net/http` のエコシステムを手放すことなので、
思い込みではなく計測で確認してください。

## 自分のアプリケーションを測る

プロファイラは別のリスナーに載せ、計測対象の mux を変えないようにします。
todo の 2 サービスはどちらも `pprof.go` で、環境変数が設定されたときだけ
有効になります。

**問いに合った計器を選んでください。**間違えると自信たっぷりに誤導されます。

| 知りたいこと | 計器 |
| --- | --- |
| どの関数が CPU を焼いているか | CPU プロファイル |
| ロック待ちしているか | mutex プロファイル（`SetMutexProfileFraction`） |
| goroutine がどこで park するか | block プロファイル（`SetBlockProfileRate`） |
| その層が原因か | **その層を差し替えて測り直す** |

最後の行はプロファイルではなく、そして議論に決着をつけるのはこれです。
todo サービスの CPU プロファイルでは `database/sql.withLock` がサンプルの 15% を
占め、直列化の問題に見えます。ところがベースラインを同じ `database/sql` 層に
載せ替えても 3% しか動きませんでした。ロックは律速ではなかった。誤読の原因は
2 つで、CPU プロファイルはそもそも競合を見せられない（mutex 待ちの goroutine は
park していてサンプルされない）こと、そして cum 値はその関数が呼んだもの
（ここではドライバのクエリ実行）を全部含むこと。どちらも同じ方向へ間違えます。

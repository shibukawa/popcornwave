フレームワークのセキュリティは、ハンドラを 1 行も書かないうちにかなりの部分が
決まっています。常に有効な防御もあれば、設定しなければ動かないもの、アプリケーションが
責任を持つものもあります。無効だと分かっていれば対処できますが、有効だと思い込んだ防御の
穴は見つけにくいものです。

以下では、リクエストがどの検査を通るかに沿って、それぞれの担当範囲を整理します。
Popcorn Wave は危険なリクエストを拒否できますが、アプリケーション固有の操作を誰に
許可するかまでは決められません。

## リクエストが通る順序

リクエストはチェインを通ってハンドラに届きます。この順序は恣意的ではありません。
それぞれの段が、上の段がすでに走っていることを前提にしています。

| 段 | 決めること |
| --- | --- |
| 運用エンドポイント | ヘルスチェック、レディネス、フレームワークのアセットが最上位で応答する |
| 公開アセット | 静的ファイルはルートに触れずに返る |
| ボディ上限 | 大きすぎるボディは読む前に拒否する |
| セキュリティヘッダ | ブラウザに適用させるレスポンスポリシー |
| リカバリ | パニックが切断ではなくレスポンスになる |
| **セッション** | クッキーが検証済みレコードになる。ならなければ匿名リクエスト |
| **認証** | ログイン系エンドポイントが自分のパスに応答する |
| **CSRF** | 更新系リクエストが、自分のページ由来であることを示す |
| **ガード** | 保護対象パスへの未認証リクエストをログインへ送る |
| ハンドラ | — |

太字の3段が、身元が権限に変わる場所です。その上はリクエストの形の話で、
セッション以降は誰が投げたのかの話になります。

CSRF が認証より下にあるのには理由があって、これは見落としやすい。ログイン系
エンドポイントは上位で応答するので、ログイン POST も OIDC コールバックもトークンを
必要としません。そもそも検査に到達しないからです。設定で除外しているのではなく、
段の位置から自然にそうなります。

## 既定で動いているもの

何も設定していないプロジェクトを守るものが3つあります。

**レスポンスヘッダ。** `X-Content-Type-Options`、`X-Frame-Options`、リファラポリシーが
全レスポンスに乗ります。自分で書く必要がある2つについては
[セキュリティヘッダ](/ja/guides/frontend/security-headers/)を参照してください。

**エスケープ。** テンプレートは型付きの穴から値を差し込み、それぞれが着地する位置に
応じてエスケープされます。生のマークアップを出すには明示的なイントリンシックが要るので、
ヘルパの内側に隠れず、レビューで見えます。

**不透明なセッショントークン。** ブラウザが持つのは 256 ビットのランダム値です。
ストアの鍵はその SHA-256 ハッシュなので、データベースのダンプが漏れても、そのままでは
クッキーとして再生できません。

## 設定を1行待っているもの

**CSRF** は、対象パスを指定するまで無効です。これは意図的で、何も覆っていない検査は
「保護がある」と読めてしまいます。`csrf.include = []` は `csrf.enabled = false` より
性質の悪い嘘です。

`pw init` は形だけ書いて、無効のまま残します。

```toml
[security]
csrf.enabled = false
csrf.include = ["/**"]
csrf.exclude = []
```

**パス保護**も同じ形です。`protection.include = []` は全パスが公開という意味で、
プロジェクトはルートを除外するのではなく、追加していきます。

**HSTS** は、証明書について確信が持てるまで無効です。すでにキャッシュしたブラウザに
対して、有効化を取り消すのが難しいからです。

## CSRF の仕組み

CSRF トークンは、リクエストがサーバの描画したページから来たことを示します。仕組みとしては、
サーバが知っていて攻撃者のページからは読めない秘密値です。

### 秘密値

セッションごとに1つ、セッション生成時に作られてセッションレコードに入ります。
ローテーションは自動です。ログインはセッションを置き換え、秘密値もそれに従うので、
ログイン前に作られたトークンはログイン後には通りません。

秘密値はハンドラに届きません。コードが読むセッションビューからは意図的に外してあり、
テンプレートのスコープにも入りません。

### 3つの経路

トークンは3つの経路でブラウザに届き、いずれも同じ1つの秘密値に対して検証されます。

| 経路 | 書くもの | 読むもの |
| --- | --- | --- |
| hidden フィールド | テンプレートコンパイラが、全 unsafe form に | 素のフォーム送信 |
| `pw_csrf` クッキー | セッションマネージャが、セッションクッキーと並べて | ブラウザランタイム |
| `X-CSRF-Token` ヘッダ | ランタイムが、クッキーから読んで | サーバ |

hidden フィールドは、書かなくてよい部分です。`<form method="post">`（put、patch、
delete も）には、生成時に第一子として自動で入ります。GET フォームには入りません。
フィールドがクエリ文字列になるので、URL に載ったトークンは履歴・ログ・リファラに残ります。

同じページでも、2種類のフォームは実行時ではなく生成時に落ちます。クロスオリジンに
POST するフォーム — セッションの秘密値を第三者に渡すことになる — と、method が
計算値のフォームです。後者は safe か unsafe か判別できません。

### クッキーがある理由

ヘッダの値はページから取ることもできました。そうしていないのは、ローテーションのためです。

描画済み HTML に埋め込んだトークンは、render 時点で固定されます。ページを開いたまま
セッションがローテートすると — 別タブでのログイン、権限の変更 — サーバが受け付けない
トークンを持ったままになり、次の操作が失敗します。画面には理由が何も出ません。
リクエストを出す瞬間にクッキーを読めば、これが閉じます。ローテーションが新しいクッキーを
書いているので、ランタイムは次のリクエストでそれを拾います。

Django も Laravel も Spring の SPA 構成も同じ形です。代償は JavaScript から読める
クッキーが1つ増えることで、これがフレームワークのクッキーを `HttpOnly` にするという
規則の、唯一の明示された例外になります。読めないランタイムは送れません。

### 毎回バイトが変わる理由

出力のたびに新しいランダムパッドが乗るので、同じページを2回描画するとトークンのバイト列は
変わります。復元される秘密値は同じです。

理由は圧縮です。レスポンスは圧縮されるので、攻撃者が影響を与えられるテキスト — 
エコーバックされた検索語、再表示されたフォームの値 — と同じ圧縮ボディの中に、
変化しない秘密値が入っていると、レスポンスサイズを観察して1バイトずつ取り出せます。
レスポンスごとに変わるパッドは、蓄積するものを残しません。

検証は、届いたリクエストが運んできたパッドから期待値を再構築し、定数時間で比較します。
Rails も Django も同じ理由でマスクしています。

### 匿名の訪問者

トークンには秘密値が要ります。公開ページに自前の unsafe form がある場合 — 問い合わせ
フォーム、POST 検索 — 秘密値を取ってくるログインがありません。

専用の仕組みは要りませんでした。秘密値は
[登録されたセッションスロット](/ja/guides/storage/session-storage/#csrf-の秘密値)で、
配置は `session.Private`。private なスロットはセッションが匿名のあいだ封をしたクッキーに
載ります。だから匿名の訪問者は秘密値を得て、ストアには行が増えない。ページを読んだ
クローラが払うのはクッキー1つで、レコードではありません。

サインインすると、ログイン時のローテーションが同じスロットを設定されたバックエンドへ
移し、新しい秘密値を作ります。匿名側が残ることはありません。そもそも 2 つ目が存在しない
からです。1つのスロットが両方の母集団を賄い、ここに固有の設定は 1 つもありません。

一時期は分かれていました。認証済みはレコードのフィールド、匿名は署名クッキー、専用の鍵と
専用の opt-in 付きで。分けていた理由は「匿名トラフィックにストアの行数を決めさせない」
ことでしたが、private なスロットをログインまでクッキーに置くことが同じ問いに答えたので、
2 つ目の仕組みは消えました。

### 拒否されたとき

拒否されたリクエストは、他と同じエラー経路で 403 になります。ブラウザなら自分の HTML
エラーページ、API クライアントなら problem ドキュメントです。ハンドラは呼ばれません。

レスポンスは、どの検査で落ちたかを言いません。理由はログに出ます。レスポンスで名指しすると、
攻撃者にどちらを詰めればいいかを教えることになるからです。

## 自分で持つもの

以下はフレームワークが決めません。

**認可。** 検証済みセッションは誰が要求しているかを言うだけで、何をしてよいかは言いません。
パス保護はルート単位で、それより細かいものはハンドラの仕事です。

**どのパスが unsafe か。** `csrf.include` を狭めるのは自分の判断です。`csrf.exclude` も
同じで、webhook はそこに入ります。セッションを持たず、自前の認証を運んでくるからです。

**登録したコンポーネントの入力。** コンポーネントを再描画可能として公開すると、その
パラメータは攻撃者が操作できる値になります。渡された値を整形するだけのコンポーネントは
安全ですが、識別子でレコードを読むものは、ハンドラと同じように所有権を自分で確認する
必要があります。登録がレビューの地点です。

**設定の中の秘密値。** secret として分類された値はログと起動サマリから伏せられ、
`pw doctor` はコミットされたファイル内のリテラルな秘密値を報告します。ただし、
その値がすでに漏れていたかどうかまでは分かりません。

## 開発だけに許されていること

`APP_ENV` によって意味が変わる設定がいくつかあります。どれもリクエストから読むことは
なく、ホスト名から推測することもありません。環境は配備が与えるトークンで、知らない値は
開発ではなく配備として扱われます。

以下の 3 つの層は分けて把握する価値があります。落ちるタイミングが違い、そのうち 1 つは
そもそも落ちないからです。

### 開発以外では起動しない

プロセスが起動しません。どれも防御を弱めるのではなく切るものなので、警告で済ませていません。

`session.cookie.secure = false` は、セッションクッキーが平文の http を通ることを許します。
`pw init` は開発用の設定ファイルに意図してこれを書きますが、`dev` 以外では設定名を挙げて
起動に失敗します。例外は `secure` なしの `same_site = none` で、こちらはどの環境でも
失敗します。そもそもその組み合わせをクロスサイトクッキーとして受け入れるブラウザが
ないからです。

`auth.jwt.dev.trust_unverified_tokens` は、署名のない手書きのベアラートークンを通します。
`curl` を持った開発者が認可サーバ無しで作業できるようにするためのものです。鍵は 4 つあり、
全部が開いている必要があります。`pwdev` ビルドモード、`stg` でも `prod` でもない
`APP_ENV`、設定そのもの、そしてループバックからのリクエスト（opt-out なし）です。タグ
無しでビルドされたバイナリは、この設定を見ただけで起動に失敗します。無視はしません。
そして緩まないものも同じくらい重要です。admission、失効、パーサの上限はいずれも効いたまま
なので、開発者は迂回路ではなく本物のルールを相手にします。

[開発用 ID プロバイダ](/ja/productivity/dev-identity-provider/)は誰の認証もしません。
サインインは一覧から利用者を選ぶだけです。だから `prod` では起動を拒否し、ループバックに
のみバインドします（opt-out なし）。`pw build` も、ビルド対象のアプリケーションがこれを
import していると失敗するので、事故でリリース成果物に混ざることはありません。`pw dev` が
どう繋ぐかは[認証](/ja/guides/backend/authentication/#開発中)にあります。

### 開発以外でも通るが、警告が出る

起動はします。起動時に警告が出て、`pw doctor` も報告します。認証を切るのではなく、可視性・
永続性・多層防御を削る種類のものなので、判断は配備に残ります。

| 設定 | `dev` 以外での代償 |
| --- | --- |
| `security.csrf.enabled = false` | unsafe なリクエストの origin もトークンも検査されない |
| `security.headers.enabled = false`、`hsts.enabled = false` | ブラウザが適用するレスポンスポリシーが弱くなる |
| `observability.query.enabled` | SQL 文が診断レコードに載る |
| `observability.query.bind_values` | 行の値も載る。アプリのデータがフレームワークの SQL レコードに入る唯一の経路 |
| `observability.minimum_level = trace` / `debug` | 配備されたプロセスで冗長なログが出る |
| `sqlite` のインメモリ DSN | スキーマも全行も再起動で消える |
| `server.public.read_local = true` | ビルド済みツリーではなくディスクから配信される |
| `auth.enabled` かつ `session.backend = cookie` | 発行済みのセッションをログアウトで終わらせられない（次節） |

最初に見るべきは `csrf.enabled` です。既定が false なので、一度も有効にしていない
プロジェクトは、選んだ覚えがないままこの行に入っています。

### 設定が無くても違うもの

エラーページは `dev` では問題をそのまま載せます。メッセージ、原因、`Problem` に持たせた
detail までです。それ以外の環境ではステータスとタイトルだけになります。これに対応する設定
項目はなく、テンプレートも両者で同じです。変わるのは渡されるものだけです。開発では読む人が
その失敗を起こした本人で、これから直す人です。それ以外では、同じページが公開されます。

1 つだけ、意図的に環境で切っていない緩和があります。`auth.oidc.allow_loopback_http` と
JWT 側の対応物は `http` の issuer を許しますが、縛っているのは `APP_ENV` ではなく
「ホストが実際にループバックであること」です。環境トークンは配備が与えるもので間違えられる
以上、こちらのほうが強い縛りです。

## 既知の限界

ここに挙げる 4 つの防御には、絶対ではなく境界があります。境界の理由はどれも現実の側に
あります。ブラウザは渡されたものを手放しませんし、ランタイムはソケットの read を途中で
やめられません。設定を強めれば消える種類のものではないので、知ったうえで設計を組む対象
として書いておきます。

### クッキーバックエンドはセッションを終わらせられない

`session.backend = cookie` は、セッションレコードをサーバに置かず、封をしてブラウザに
持たせます。運用コストが最も低く、インフラを何も必要としない唯一のバックエンドですが、
その代償が失効です。すでにブラウザに書いたレコードは取り返せません。ログアウトはクライアント
側の写しを期限切れにするだけで、それ以前に取られた写しは封の期限まで動き続けます。
アカウント停止も同じ形になります。

これをログインと組み合わせること自体は、開発では正しい判断です。データベース無しでログインが
動くことがそのバックエンドの存在理由ですし、露出させるには他人が握っているブラウザが要ります。
なので `dev` では何も言いません。それ以外の環境では起動時に警告が出て、`pw doctor` も
設定に対して `PW0506` を報告します。

```
the login session is stored where it cannot be revoked
```

どちらもプロセスは止めません。オンデマンドでセッションを終わらせられなくても構わないか
どうかを知っているのは配備だけなので、判断はそちらに残します。ただし、その警告を staging や
本番のログで読んでいるなら、答えはほぼ確実に「構う」です。`rdb`、`redis`、`dynamo`、
`firestore` の
どれかに移してください。インシデントを生き延びられるかどうかを決めるのはログアウトと停止の
2 つで、どちらもサーバが消せるレコードを必要とします。

カート、ロケール、ウィザードの途中経過のように、ログインを前提としない状態を置くだけなら、
クッキーバックエンドは今も良い選択です。

### アカウント停止が効くまで最大 30 秒かかる

停止されたアカウントはログイン時に拒否されます。すでにセッションを持っているリクエストでも
拒否されます。生きているセッションの背後にあるアカウントを、リクエストの流れの中で読み直す
からです。ただし 1 アカウントあたり 30 秒に 1 回までです。毎リクエスト読むと、認証済みの
全ページの前にデータベースの往復が 1 回入ることになります。

この間隔が、「すでに握られているセッションに停止が届くまでの時間」に対する正直な答えです。
停止を実行する場所から `auth.ForgetAccount(accountID)` を呼べば、次のリクエストで即座に
読み直されます。ただしプロセスローカルなので、複数インスタンスで動かしている配備では、
他のインスタンスは結局この間隔を待ちます。

アカウントストアにまったく到達できないときは、通過させるでもサインアウトさせるでもなく、
503 で拒否します。資格情報はまだ判定されておらず、リトライで成功する余地があり、そして
障害中に通過させてしまうと、すべての停止がアカウントデータベースの稼働を前提にした
ものになってしまうからです。

### TinyGo ビルドではタイムアウトを自前で効かせている

TinyGo の `net/http` は、接続したあと期限なしで read します。これは推測ではなく、
その実装自身が `TINYGO: TODO handle timeouts` というコメントでそう書いています。つまり
OIDC ディスカバリ、トークン交換、JWKS 取得を `context.WithTimeout` で囲んでも何も
縛れず、遅い IdP がリクエストハンドラを相手が切るまで掴んだままにできます。

そこで OIDC と JWT のクライアントは、TinyGo ビルドでは transport を包み、期限が来たら
呼び出し側に必ず戻るようにしています。包んでも解決できないのは、その下で走っている
ラウンドトリップ自体をキャンセルすることです。あのランタイムにキャンセルの口がないことが、
そもそもの理由だからです。したがって固まった IdP のコストは、止まったハンドラではなく、
ソケットが自分で失敗するまでのゴルーチン 1 本とコネクション 1 本になります。リクエストは
処理され続けますが、負荷が続く状況で永遠に固まる IdP は、やはりアラートに値します。

これはホスト Go のビルドでは再現しません。`force_tinygo_logic` でも同じです。あのタグは
TinyGo 側のコード経路を選びますが、リンクされる `net/http` はホストのものだからです。
タイムアウトの挙動は、実際のツールチェーンで試すしかない数少ない項目の 1 つです。

### キャッシュした JWKS の鍵は障害中でも期限切れになる

検証鍵は issuer から取得してキャッシュします。更新に失敗したときは、キャッシュ済みの鍵を
そのまま使い続けます。issuer に到達できないことは、その鍵が間違っていることを意味しない
からです。ただしそれはキャッシュ TTL を過ぎてから 1 時間までで、その先は検証が失敗する
側に倒れます。

理由は、公開されている文書から取り下げられた鍵は、そう書いてある文書をこのプロセスが
読めるかどうかとは無関係に取り下げられている、ということです。stale の窓に上限がないと、
侵害された鍵は障害が続くかぎり使えることになり、それは攻撃者にとって都合よく選べる窓に
なります。既定は 1 時間で、`MaxStaleAge` で 24 時間まで動かせます。「無期限」にする設定は
意図的に用意していません。

## 何が有効かを確認する

`pw doctor` は、指定した環境のマージ済み設定を読んで、無効になっているものを報告します。

```bash
pw doctor --env prod
```

無効な CSRF 検査、`secure` のないセッションクッキー、弱められたレスポンスヘッダ、
開発以外で有効なままのクエリ診断を指摘します。開発マシンから本番設定に対して走らせることに
意味があります。findings は動いているプロセスではなく、ファイルについてのものだからです。

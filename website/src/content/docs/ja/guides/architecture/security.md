フレームワークのセキュリティは、ハンドラを1行も書かないうちにほとんど決まっています。
問題は、何も書いていない状態でどれが動いていて、どれが設定を待っていて、どれが最初から
自分の責任なのか、です。有効だと思い込んでいた防御は、無効だと知っている防御より
たちが悪い。

このページでは、リクエストが通る検査を順に追ってから、その経路の外側にあるものを扱います。

## リクエストが通る順序

リクエストはチェインを通ってハンドラに届きます。この順序は恣意的ではありません。
それぞれの段が、上の段がすでに走っていることを前提にしています。

| 段 | 決めること |
| --- | --- |
| 運用エンドポイント | ヘルスチェック、レディネス、フレームワークのアセットが最上位で応答する |
| 公開アセット | 静的ファイルはルートに触れずに返る |
| ボディ上限 | 大きすぎるボディは読む前に拒否する |
| セキュリティヘッダ | ブラウザに適用させるレスポンスポリシー |
| リカバリ | パニックが切断ではなくレスポンスになる |
| **セッション** | クッキーが検証済みレコードになる。ならなければ匿名リクエスト |
| **認証** | ログイン系エンドポイントが自分のパスに応答する |
| **CSRF** | 更新系リクエストが、自分のページ由来であることを示す |
| **ガード** | 保護対象パスへの未認証リクエストをログインへ送る |
| ハンドラ | — |

太字の3段が、身元が権限に変わる場所です。その上はリクエストの形の話で、
セッション以降は誰が投げたのかの話になります。

CSRF が認証より下にあるのには理由があって、これは見落としやすい。ログイン系
エンドポイントは上位で応答するので、ログイン POST も OIDC コールバックもトークンを
必要としません。そもそも検査に到達しないからです。設定で除外しているのではなく、
段の位置から自然にそうなります。

## 既定で動いているもの

何も設定していないプロジェクトを守るものが3つあります。

**レスポンスヘッダ。** `X-Content-Type-Options`、`X-Frame-Options`、リファラポリシーが
全レスポンスに乗ります。自分で書く必要がある2つについては
[セキュリティヘッダ](/ja/guides/frontend/security-headers/)を参照してください。

**エスケープ。** テンプレートは型付きの穴から値を差し込み、それぞれが着地する位置に
応じてエスケープされます。生のマークアップを出すには明示的なイントリンシックが要るので、
ヘルパの内側に隠れず、レビューで見えます。

**不透明なセッショントークン。** ブラウザが持つのは 256 ビットのランダム値です。
ストアの鍵はその SHA-256 ハッシュなので、データベースのダンプが漏れても、そのままでは
クッキーとして再生できません。

## 設定を1行待っているもの

**CSRF** は、対象パスを指定するまで無効です。これは意図的で、何も覆っていない検査は
「保護がある」と読めてしまいます。`csrf.include = []` は `csrf.enabled = false` より
性質の悪い嘘です。

`pw init` は形だけ書いて、無効のまま残します。

```toml
[security]
csrf.enabled = false
csrf.include = ["/**"]
csrf.exclude = []
```

**パス保護**も同じ形です。`protection.include = []` は全パスが公開という意味で、
プロジェクトはルートを除外するのではなく、追加していきます。

**HSTS** は、証明書について確信が持てるまで無効です。すでにキャッシュしたブラウザに
対して、有効化を取り消すのが難しいからです。

## CSRF の仕組み

CSRF トークンは、リクエストがサーバの描画したページから来たことを示します。仕組みとしては、
サーバが知っていて攻撃者のページからは読めない秘密値です。

### 秘密値

セッションごとに1つ、セッション生成時に作られてセッションレコードに入ります。
ローテーションは自動です。ログインはセッションを置き換え、秘密値もそれに従うので、
ログイン前に作られたトークンはログイン後には通りません。

秘密値はハンドラに届きません。コードが読むセッションビューからは意図的に外してあり、
テンプレートのスコープにも入りません。

### 3つの経路

トークンは3つの経路でブラウザに届き、いずれも同じ1つの秘密値に対して検証されます。

| 経路 | 書くもの | 読むもの |
| --- | --- | --- |
| hidden フィールド | テンプレートコンパイラが、全 unsafe form に | 素のフォーム送信 |
| `pw_csrf` クッキー | セッションマネージャが、セッションクッキーと並べて | ブラウザランタイム |
| `X-CSRF-Token` ヘッダ | ランタイムが、クッキーから読んで | サーバ |

hidden フィールドは、書かなくてよい部分です。`<form method="post">`（put、patch、
delete も）には、生成時に第一子として自動で入ります。GET フォームには入りません。
フィールドがクエリ文字列になるので、URL に載ったトークンは履歴・ログ・リファラに残ります。

同じページでも、2種類のフォームは実行時ではなく生成時に落ちます。クロスオリジンに
POST するフォーム — セッションの秘密値を第三者に渡すことになる — と、method が
計算値のフォームです。後者は safe か unsafe か判別できません。

### クッキーがある理由

ヘッダの値はページから取ることもできました。そうしていないのは、ローテーションのためです。

描画済み HTML に埋め込んだトークンは、render 時点で固定されます。ページを開いたまま
セッションがローテートすると — 別タブでのログイン、権限の変更 — サーバが受け付けない
トークンを持ったままになり、次の操作が失敗します。画面には理由が何も出ません。
リクエストを出す瞬間にクッキーを読めば、これが閉じます。ローテーションが新しいクッキーを
書いているので、ランタイムは次のリクエストでそれを拾います。

Django も Laravel も Spring の SPA 構成も同じ形です。代償は JavaScript から読める
クッキーが1つ増えることで、これがフレームワークのクッキーを `HttpOnly` にするという
規則の、唯一の明示された例外になります。読めないランタイムは送れません。

### 毎回バイトが変わる理由

出力のたびに新しいランダムパッドが乗るので、同じページを2回描画するとトークンのバイト列は
変わります。復元される秘密値は同じです。

理由は圧縮です。レスポンスは圧縮されるので、攻撃者が影響を与えられるテキスト — 
エコーバックされた検索語、再表示されたフォームの値 — と同じ圧縮ボディの中に、
変化しない秘密値が入っていると、レスポンスサイズを観察して1バイトずつ取り出せます。
レスポンスごとに変わるパッドは、蓄積するものを残しません。

検証は、届いたリクエストが運んできたパッドから期待値を再構築し、定数時間で比較します。
Rails も Django も同じ理由でマスクしています。

### 匿名の訪問者

トークンには秘密値が要り、秘密値は通常セッションから来ます。公開ページに自前の
unsafe form がある場合 — 問い合わせフォーム、POST 検索 — そのどちらもありません。

匿名訪問者ごとにセッションを発行すれば動きますが、割に合いません。そのページへの
未認証リクエストが1つ来るたびに行が書かれるので、**行数を決めるのはクローラであって
ユーザー数ではありません**。しかもログアウトがないので、それらの行は削除されず期限切れを
待つことになります。

そこで、秘密値そのものをクッキーに置き、署名します。

```toml
csrf.anonymous.enabled = true
csrf.anonymous.secret = "${SECURITY_CSRF_ANONYMOUS_SECRET}"
```

検証は読み出しではなく署名の再計算なので、匿名の母集団を覚えるコストはゼロです。
この署名が、naive double-submit — クッキーを設定できる者なら誰でも検査を満たせる形 — 
との違いを作っています。

セッションの秘密値が常に優先されるので、ログインしても匿名側が残ることはありません。

### 拒否されたとき

拒否されたリクエストは、他と同じエラー経路で 403 になります。ブラウザなら自分の HTML
エラーページ、API クライアントなら problem ドキュメントです。ハンドラは呼ばれません。

レスポンスは、どの検査で落ちたかを言いません。理由はログに出ます。レスポンスで名指しすると、
攻撃者にどちらを詰めればいいかを教えることになるからです。

## 自分で持つもの

以下はフレームワークが決めません。

**認可。** 検証済みセッションは誰が要求しているかを言うだけで、何をしてよいかは言いません。
パス保護はルート単位で、それより細かいものはハンドラの仕事です。

**どのパスが unsafe か。** `csrf.include` を狭めるのは自分の判断です。`csrf.exclude` も
同じで、webhook はそこに入ります。セッションを持たず、自前の認証を運んでくるからです。

**登録したコンポーネントの入力。** コンポーネントを再描画可能として公開すると、その
パラメータは攻撃者が操作できる値になります。渡された値を整形するだけのコンポーネントは
安全ですが、識別子でレコードを読むものは、ハンドラと同じように所有権を自分で確認する
必要があります。登録がレビューの地点です。

**設定の中の秘密値。** secret として分類された値はログと起動サマリから伏せられ、
`pw doctor` はコミットされたファイル内のリテラルな秘密値を報告します。ただし、
その値がすでに漏れていたかどうかまでは分かりません。

## 何が有効かを確認する

`pw doctor` は、指定した環境のマージ済み設定を読んで、無効になっているものを報告します。

```bash
pw doctor --env prod
```

無効な CSRF 検査、`secure` のないセッションクッキー、弱められたレスポンスヘッダ、
開発以外で有効なままのクエリ診断を指摘します。開発マシンから本番設定に対して走らせることに
意味があります。findings は動いているプロセスではなく、ファイルについてのものだからです。

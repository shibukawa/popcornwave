ハンドラが動く時点で、セッションの問いはすでに終わっています。ミドルウェアがクッキーを
読み、ハッシュにし、レコードを取り、2つの期限を確認して、検証済みのセッションを置いたか
置かなかったかのどちらかです。ハンドラが尋ねるのは、その結果だけです。

```go
func mypage(w http.ResponseWriter, r *http.Request) {
	view, ok := session.Read[auth.SessionData](r.Context())
	if !ok {
		// 匿名リクエストはエラーではなく通常の状態です。
		return
	}
	_ = view.Data       // 型付きのペイロード
	_ = view.ExpiresAt  // 権威ある期限
	_ = view.Method     // "oidc" など、どう認証されたか
}
```

`Read` はペイロード型に対するジェネリックで、この型パラメータはキャストではなく検査です。
別のペイロードを持つレコードは、レコードが無いときとまったく同じように `false` を返します。

| フィールド | 意味 |
| --- | --- |
| `Data` | 型付きのペイロード |
| `CreatedAt` | セッションが始まった時刻 |
| `AuthenticatedAt` | 最後にログインを通った時刻。トークン更新でリセットされる |
| `LastSeenAt` | ストアが記録した最後の活動 |
| `ExpiresAt` | 絶対期限 |
| `IdleExpiresAt` | 無操作期限。設定がなければゼロ |
| `Method` | `"oidc"` など、どう認証されたか |
| `Version` | ペイロードのスキーマ版。古いレコードを無効化するためのもの |

ここにある時刻はすべてサーバーのものです。ブラウザが送ってきた値が主張できるものは 1 つも
ありません。だから「セッションは何時まで」と出すなら `ExpiresAt` から描き、作業に応じて動く
期限のほうが `IdleExpiresAt` です。

`plugin/auth` を使っているなら、同じレコードへのより扱いやすい入口が
[`auth.User`](/ja/guides/backend/authentication/#ユーザーを読む) です。どちらにせよ、ハンドラが
トークンや鍵ハッシュ、バックエンドのクライアントを見ることはありません。どのバックエンド
だったかも見えません。あるデプロイはセッションをテーブルに、次のデプロイは DynamoDB に
置く——その間にハンドラの修正が 1 行も挟まらないのは、そのためです。レコードが実際にどこに
あるかは[セッションストレージ](/ja/guides/storage/session-storage/)の話です。

## セッションが無いとき

`ok` が false になるのは、そもそもセッションが無かったリクエストと、クッキーが無い・壊れて
いる・期限切れのリクエストです。いずれも明示的に未認証として続行され、古いクッキーは
消されます。サーバーが受け付けないクッキーを持ち続けるブラウザには、送るのをやめてもらう
のが筋だからです。

バックエンドに到達できない場合は別の答えになります。ミドルウェアは黙って匿名に格下げせず
`503` を返します。「データベースが落ちている」と「ログインしていない」が、表示を決める
アプリケーションから同じに見えてはいけないからです。ストレージ障害でサインインを促す画面を
出すことは、ユーザーに嘘をつき、しかもログインし直せば直ると誘っていることになります。

だから `Read` は、そのリクエストを通してよいかを判断しません。`false` が返る時点で、その
判断は正しく下せる場所ですでに終わっています。ルートを守るのは
[認証](/ja/guides/backend/authentication/)です。`Read` は、誰がいるかによって描き分ける
ハンドラのためのものです。

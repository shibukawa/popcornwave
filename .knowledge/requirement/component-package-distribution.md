---
id: requirement:component-package-distribution
type: requirement
title: Component Package Distribution
---
A capability built once must be publishable as a Go module and consumable by an application that never runs the generator over it.

```yaml
priority: should
motivation:
  - vision:popcorn-web targets one application, so every reusable capability today is either in this repository or copied by hand
  - api:cli-add installs a capability by writing files, which drifts from the version that wrote them and cannot be published by anyone else
  - a component is a template, a script, some Go, and a migration; only the Go half has a distribution mechanism today
actor: actor:application-developer, in two roles that are otherwise the same person
scope:
  unit: concept:component-package
  publishing: ordinary Go module publishing, with no registry, index, or plugin format of our own
  consumption: flow:component-package-consumption
  authoring: api:cli-package
as_built:
  status: stage one is implemented
  config: project.kind, the packages array, and the package manifest section, in the project loader
  runtime: pw.RegisterPackage carrying Module, Version, Assets, and Migrations; pw.Packages reports what the binary linked
  assets: served from embedded bytes at /_pw/pkg/{digest}/{name}, deduplicated by content digest, above the reserved namespace close
  linking: api:cli-generate emits the blank import of every declared package into the existing bootstrap linker
  schema: one goose provider per package stream over popcornweb_migrations_{stem}, applied in module graph order before the application's
  install: pw add {module-path} writes the go.mod requirement and one declaration, and copies nothing
  diagnosis: PW0140 an unresolvable declaration, PW0141 a linked package the project never declared, PW0143 a package generated by a newer framework
  not_built:
    - api:cli-package scaffolding, so a package repository is still assembled by hand
    - a doctor check for an unapplied package stream, because doctor opens no database on that path; api:cli-migrate reports pending stream versions instead
staged:
  stage_one:
    delivers: the feature shape of concept:component-package
    needs_upstream: nothing
    proves: committed artifacts, api:package-registration, requirement:package-schema-contribution, and requirement:package-asset-delivery
  stage_two:
    delivers: the component-library shape
    needs_upstream: requirement:cross-package-components, and requirement:package-component-assets for a component that carries a script
    blocked_until: system:tinybind resolves what an external component declaration may name
  why_staged: the first stage is the larger share of the value and the whole of the tooling work, and holding it for an upstream round would ship neither
rules:
  - a package is generated by its own repository and commits what it generated, per decision:committed-package-artifacts
  - a consumer builds a package's generated code with the Go compiler alone, so no build step in the consumer reaches into the module cache
  - installing is one declaration in data:project-config and nothing copied, per decision:declared-package-installation
  - a package contributes through one Go entry point and one manifest, per decision:package-contract-split
  - a package that contributes nothing but Go needs neither, and stays an ordinary Go module
  - a package names the pw and system:tinybind versions it generated against, and policy:package-compatibility decides what the consumer does with them
  - no capability of a package is discovered by scanning; every contribution is declared by the package and every package is declared by the project
acceptance:
  - an application acquires a middleware, a configuration section, a schema, and a browser asset by naming one module in data:project-config, with no other edit
  - an application acquires a page tree the same way, plus the one Register call decision:declared-package-installation deliberately kept
  - no file is written into the project tree by the install
  - the same application builds with go build alone after api:cli-generate has run for its own sources, and the dependency is not regenerated
  - a package published with a stale generated artifact fails to compile in the consumer, naming the package
  - api:cli-check in the consumer passes without reading any dependency
  - a package's own CI runs api:cli-check over the package and fails on a stale commit
  - two packages contributing an asset with identical bytes serve one URL
  - a TinyGo application links a package and stays inside rule:tinygo-runtime-compatibility
  - a package the application imports but does not enable adds no route, no configuration key, and no table
non_goals:
  - a plugin format loaded at runtime, which rule:tinygo-runtime-compatibility and the reflection-free generated path both forbid
  - a package registry, version resolver, or lockfile of our own
  - regenerating a dependency from the consumer, which the system:tinybind modular package generation rule forbids upstream and the read-only module cache forbids here
  - removing a package from a project, matching the requirement:incremental-project-capabilities non-goal
  - .pw.sql in a package for the first shape; a generated query carries one dialect's placeholders and the package cannot know the consumer's engine, so the query stays handwritten until system:tinybind can emit one package per engine
related:
  - concept:component-package
  - api:package-registration
  - data:component-package-manifest
```

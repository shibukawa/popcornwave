---
id: requirement:template-source-positions
type: requirement
title: Template Positions In Generated Go
---
A position inside generated Go resolves to the .pw.* line that produced it, so a compiler error, a panic, and a debugger step name the template rather than a *_pw_gen.go the developer never wrote.

```yaml
status: implemented. system:tinybind v0.5.17 emits the directives behind Options.TemplateLineDirectives; api:cli-generate reads data:project-config generate.line_directives into it and resolves the restore placeholder against the name it writes under
audience: actor:application-developer
mechanism: decision:template-position-mapping
downstream_wiring:
  what: the generator states a suggested base name and the caller chooses the suffix, so a restore directive names a placeholder until the artifact has a name
  where: every point that produces generated bytes before comparing them against the tree, which is the artifact render and appendIfChanged; generator.ResolveTemplatePositions is a no-op on content carrying no directive
  why_before_the_comparison: the same reason the fasthttp build constraint is applied there — a source resolved after the comparison would read as changed on every run and make api:cli-check call a freshly generated project stale
  cost_of_skipping: a scaffolding error reports a synthetic file that does not exist; a template position is unaffected
problem:
  - policy:generated-artifacts makes *_pw_gen.go uncommitted output, so every position reported inside it names a file the developer did not write and cannot bookmark
  - a type error in a template expression surfaces as a Go error on a generated line, and the developer maps it back by reading the generated file
  - a panic inside a generated renderer names the generated file, so a deployed stack trace does not name the template
  - requirement:editor-navigation already calls the generated file a waypoint; today it has no positions to route through
covers:
  html: component and page renderers of flow:template-generation
  sql: the statement functions of a .pw.sql
  dynamo: the statement functions of a .pw.dynamo
  generated_tests: so a failure names the template rather than the emitted assertion
  scaffolding: not mapped; a line the generator wrote for itself keeps its own position, per decision:template-position-mapping
consumers:
  go_toolchain: compiler and vet findings report the template position with no *_pw_gen.go path in the message
  runtime:
    sql: a panic in a generated statement function carries the template position, because sqlbind emits a real function body whose statements the directives sit above
    html: no position. htmlbind emits a plan of instructions and a one-line binder, so the rendering happens inside the shared runtime walking that plan and the stack frame is in the library rather than in generated code. A directive cannot reach it
    why_not_fixed: the plan is a tree — a For body is a bare []Op of another scope type rather than a Plan — so a position list beside Plan.Ops misses exactly the loop bodies where a failure is most likely. Reaching them costs either a field on every op, including the Static ones that dominate a plan and that decision:force-tinygo-logic sizes, or a change to the public op constructors. Neither is worth a cost this framework has never actually paid: no case of an html render-time error being hard to locate is on record
  debugger: a breakpoint on a template body line stops in the generated function
  gopls: hover and diagnostics inside an opened *_pw_gen.go point back to the source
  language_server: requirement:editor-diagnostics can place a generation finding without reparsing, because the emitted file already carries the position
relation_to_asset_maps:
  distinct_from: requirement:derived-asset-pipeline, whose source maps describe TypeScript and reach the browser
  shared_question: whether a release artifact keeps the mapping, which requirement:deployed-debug-information already frames for the asset half
switch:
  where: data:project-config, per project rather than per command, because api:cli-generate output that depended on who ran it would make api:cli-check report drift on every machine
  default: off, matching the generator's own default; a project turns it on and gives up go test -cover for it
non_goals:
  - a side-car map file; the mapping travels inside the generated Go
  - an html render-time position, per the runtime note above
  - mapping into a system:tinybind internal the developer never opens
  - changing what api:cli-generate emits beside the mapping
  - a debugger or profiler of Popcorn Web's own, which vision:editor-support excludes
acceptance:
  - a type error in a template expression reports the .pw.html path and line
  - a panic in a generated statement function produces a stack frame naming the .pw.sql
  - an html render-time error names no template position, and that is written down rather than left to be discovered
  - api:cli-check output is unchanged, because the mapping is a property of the emitted file rather than of the check
  - a generated file with no template origin for a line reports that line as its own
  - go test over a package holding generated code still runs; go test -cover does not, and the project setting is what a reader turns off to get it back
```

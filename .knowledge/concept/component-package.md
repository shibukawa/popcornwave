---
id: concept:component-package
type: concept
title: Component Package
---
A component package is a Go module that ships Popcorn Wave sources together with their generated artifacts, so an application acquires a capability by importing it rather than by scaffolding it.

```yaml
motivation:
  today: every Popcorn Wave source belongs to one application, is generated by that application's api:cli-generate run, and is excluded from version control by policy:generated-artifacts
  consequence: a reusable component can be published as ordinary Go, and cannot be published as a component, because nothing regenerates it in the consumer
  reach: vision:contrib already publishes reusable Go inside this repository; this is the same reach for third parties and for sources the generator owns
inverted_properties:
  generation_site: the package generates itself once, at publish time, rather than in every consumer
  version_control: generated Go is committed, per decision:committed-package-artifacts
  entry_point: there is none; concept:application-entry-point stays in the consumer
  configuration: the package declares runtime configuration and never selects an environment file
shapes:
  feature_package:
    contains: handlers, a concept:page-tree, api:framework-extension registrations, generated request binding, and its own templates
    consumer_contact: one declaration in data:project-config, plus a Register call when it serves routes, per decision:declared-package-installation
    upstream_dependency: none; it is expressible with committed artifacts alone
  component_library:
    contains: .pw.html components the consumer's own templates call
    consumer_contact: an external component declaration in a consumer template
    upstream_dependency: requirement:cross-package-components, which system:tinybind has not built
  ordering: the feature shape ships first because it needs nothing upstream, per requirement:component-package-distribution
may_contain:
  - .pw.html components and their generated renderers
  - handlers, their routes, and their generated binding
  - a concept:page-tree and its api:page-registry
  - api:framework-extension registrations and their runtime configuration
  - a migration stream, contributed through requirement:package-schema-contribution
  - browser assets, delivered through requirement:package-asset-delivery
may_not_contain:
  - concept:application-entry-point, because the consumer owns the binary
  - a requirement:nested-html-templates document shell, because decision:implicit-document-shell registers exactly one and it is the application's
  - an environment configuration file, because policy:config-file-resolution resolves those in the consumer
  - .pw.sql, for the first shape only, because a generated query is compiled for one engine and a package cannot know the consumer's
contracts:
  runtime: api:package-registration, the Go entry point linked only when the package is imported
  tooling: data:component-package-manifest, the file the consumer's CLI reads without compiling anything
  split_rationale: decision:package-contract-split
boundaries:
  - a package is an ordinary Go module, so go.mod, go get, and the module proxy are the whole distribution mechanism
  - the consumer's api:cli-generate never reads a dependency's sources, so a package that failed to commit an artifact fails to compile rather than being repaired
  - concept:public-package-boundaries applies unchanged; a package imports pw and its own generated code imports pwruntime
related:
  - requirement:component-package-distribution
  - flow:component-package-consumption
  - policy:package-compatibility
```
